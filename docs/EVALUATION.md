# Agent 系统评测

本项目评测体系的完整说明。**焦点是 agent 层**——即「系统做了哪些决策、这些决策对不对」，
而不是「回答文本好不好」。文本质量与检索质量属于 RAG 评测，见第 6 节。

- 实现位置：`internal/eval/`（框架）、`cmd/helpdesk-agent/eval_*.go`（运行入口）
- 数据集：`eval/datasets/`
- 文档状态：随一期实现；派单轴已按三段流水线重写（2026-09-24），其权威数字口径见
  `DISPATCH_PIPELINE.md §4.1`；其余二期扩展项在文中标注

---

## 1. 为什么 agent 评测与 RAG 评测不是一回事

RAG 评测回答的是「检索到的东西和生成的答案质量如何」，指标落在**文本与片段**上：
`hit_rate`、`MRR`、`faithfulness`、`answer_relevancy`、`context_precision`。

Agent 评测回答的是「系统的决策序列对不对」，指标落在**动作与流程**上：

| 维度 | RAG 评测 | Agent 评测 |
|---|---|---|
| 评价对象 | 检索结果、生成文本 | 工具选择、调用顺序、步骤数、终态 |
| 典型失败 | 没召回、答案不忠实 | 该建单没建、不该建单却建了、绕了 5 步、越权写数据 |
| 成本可观测量 | token 用量 | token + 工具调用次数 + 决策轮次 |
| 是否需要 LLM 评判 | 常见（faithfulness 等） | **不需要**（工具序列是结构化的，可精确比对） |

最关键的结构性差异：**RAG 只有一种错法（答得不对），agent 有四类各自独立的错法**：

1. **该做没做**（漏调用工具）→ 用户问题没被解决
2. **不该做却做了**（越权调用）→ 产生副作用，可能不可逆
3. **做对了但绕远**（步骤过多）→ 成本与延迟翻倍
4. **做对了但顺序错**（先建单后查重）→ 产生重复工单等业务脏数据

这四类失败的改进方向完全不同，因此**必须分轴统计**。把它们混成一个「准确率」，
就只能知道「变差了」，无法知道「该改哪里」。

---

## 2. 指标三层结构

```
第一层 汇总指标     直接对外报告，用于横向对比与回归告警
   ↓
第二层 归因指标     失败原因分桶，用于定位改进方向
   ↓
第三层 明细记录     单次调用的完整审计，用于复现具体问题
```

设计原则：**每一层都要能回答「下一步该改什么」**。只有第一层就只是分数，
只有第二层才谈得上工程价值，第三层保证任何结论可复现。

## 3. 第一层：汇总指标

### 3.1 指派评测（`make eval`）

三段流水线的每一段各占一轴（45 条样本，`eval/datasets/assignment_v2.json`）：

| 轴 | 定义 | 实测 | 有效分母 |
|---|---|---|---|
| `ServiceTop1` | 期望服务 == 解析出的首位服务 | 93.33%（42/45） | 45 |
| `Weakness` | 判弱原因一致（`none`/`low_margin`/`no_service_match`/…） | 84.44%（38/45） | 45 |
| `Winner` | 期望处理人 == 最终命中者 | 85.00%（34/40） | **40**（5 条兜底池样本无期望处理人） |
| `Stage1/2/3` | 决策落在哪一段的漏斗计数 | 35 / 0 / 10 | 45 |

分母不一致是设计使然：**兜底样本没有"正确答案是谁"**，把它们算进排序分母会虚高分数的同时
让"该兜底却直派"这类错误无处显形。报告里的每个比率都必须带自己的分母。

漏斗还有一格是 **Stage 2 = 0**：离线评测刻意不注入 chooser，所以"判弱后交给模型选"这条路径
的命中率与幻觉率属于**未测**，不是 0%。接真实模型才测得到（`make eval ARGS="-offline-stage2=false ..."`）。

### 3.2 意图路由评测（`make eval-intent`）

| 指标 | 定义 |
|---|---|
| `Accuracy` | 分类正确率（分母为全部样本） |
| `MacroF1` | 各类别 F1 的算术平均，类别不平衡时比 Accuracy 更能反映问题 |
| `ParseRate` | 模型输出可被解析为已知意图的比例 |
| `Fallback` | 因输出无法解析而回退到默认意图的样本数 |
| `ShortCircuitRate` | 可短路（无需工具循环）的样本比例，用于估算成本节省空间 |
| `ByClass` | 各类别精确率/召回率/F1 |
| `Confusion` | 混淆矩阵 |
| `PromptTokens` / `CompletionTokens` | 分类本身的成本 |

**`ParseRate` / `Fallback` 与 `Accuracy` 必须分开。** 解析失败说明提示词或输出稳定性有问题，
分类错误说明类别边界或模型理解有问题，两者的修复方向完全不同。

**关键陷阱：回退值恰好等于标注时不得计为正确。** 实测踩到过——思维链模型偶发返回空输出
（completion 仅数个 token），回退成 `knowledge` 后与标注相同，于是被计成「正确」，
准确率虚高而故障被掩盖。现在的判定是 `Parsed && Intent == want`，并为这类偶发失败加了一次重试。

**已有基线对照**（180 条中文样本，5 类）：

| 方案 | Accuracy | Macro-F1 |
|---|---|---|
| 离线关键词规则 | 54.44% | 0.5243 |
| 真实模型（deepseek-flash） | **98.33%** | **0.9813** |

关键词规则的失效点很具体：`knowledge` 精确率仅 40.80%——「怎么」这类泛词把
31 条 incident 与 17 条 chitchat 吸走。这也证明数据集**不可被关键词规则解掉**，
因此适合用来判断「分类层值不值一次模型调用」。

### 3.3 检索召回评测（`make eval-retrieval`）

| 指标 | 定义 |
|---|---|
| `RecallAtK` | 可回答查询中，相关文档出现在前 K 位的比例 |
| `MRR` | 首个相关文档排名倒数的均值 |
| `PrecisionAtK` | 取回文档中相关文档的比例（按文档去重） |
| **`FalsePositiveRate`** | **不可回答查询被检索器判为「有证据」的比例** |
| `ByReason` | 按检索失败归因分桶 |

**`FalsePositiveRate` 是这一轴最关键、也最容易被忽略的指标。** 召回率只看「该找到的找到了多少」，
而假命中意味着**模型会基于无关片段作答**——比漏召回更隐蔽，也更容易产生错误回答。

判定的混淆矩阵刻意拆成三格，因为三者改进方向不同：

```
可回答且有证据    该答的答了      正常
可回答但漏召回    该答的没敢答    检索或阈值问题
不可回答却假命中  不该答的乱答    置信判定过松
```

**已有基线**（32 段语料 / 90 条查询，K=5，BM25）：

| 指标 | 值 |
|---|---|
| Recall@5 | 92.50% |
| MRR | 0.8754 |
| Precision@5 | 28.25%（结构性偏低，见下） |
| 假命中率 | **10.00%** |
| 可回答且有证据 | 69/80 (86%) |

> `Precision@5` 偏低是结构性的而非缺陷：金标为 docId，而每个文档含 2–3 个片段，
> 因此取回 5 条时最多约 3 条能计入相关。要让它可解释需改为片段级金标。

### 3.4 轨迹评测（`make eval-trajectory`）

轨迹评测有两种驱动模式，断言完全相同，含义完全不同：

| 模式 | 触发方式 | 回答的问题 |
|---|---|---|
| `scripted`（默认） | 无密钥直接运行 | 评测链路与断言本身是否正确（自检） |
| `live` | 提供 `-api-key` 或 `LLM_API_KEY` | 真实模型的工具选择能力到底几分（测量） |

live 模式注入与 serve 一致的意图分类器，评测对象是「部署形态的系统」；
报告记录 `mode` / `model` 元数据，跨版本对比时两种口径不得混读。
单条消息设 180s 超时，瞬时失败（限流/抖动）整用例重跑一次（每条用例独立存储，重跑无副作用）。

| 指标 | 定义 | 单位 |
|---|---|---|
| `PassRate` | **全部**断言（工具/顺序/轮次/终态/成本）均满足的比例 | % |
| `ToolAccuracy` | **仅**工具集合是否命中预期 | % |
| `OrderAccuracy` | 声明了 `orderedTools` 的样本中顺序正确的比例 | % |
| `SafetyViolationRate` | 调用了 `forbiddenTools` 中任一工具的比例 | % |
| `BudgetRejectRate` | 因 `budget_exceeded` 被拒绝的比例 | % |
| `AvgRounds` | 平均模型决策轮次（路由短路的回合为 0） | 轮 |
| `AvgTools` | 平均工具调用次数 | 次 |
| `Latency.P50/P95/Max` | 端到端延迟 | **微秒** |
| `PromptTokens` / `TotalTokens` | 累计 token 用量 | token |
| `ByScenario` | 按场景分解 | % |

**首份真实基线**（deepseek-flash，16 用例，2026-09；此后数据集经口径裁决扩至 18 用例，live 待重跑）：

| 指标 | scripted（自检） | **live（测量）** |
|---|---|---|
| PassRate | 100.0% | **68.75%** |
| ToolAccuracy | 100.0% | **55.56%** |
| OrderAccuracy | 100.0% | 50.00% |
| SafetyViolationRate | 0.0% | 0.0% |
| AvgRounds | 1.67（18 用例口径） | 1.69 |
| prompt token 合计 | — | 42,277 |
| 延迟 P50 / Max | — | 3.6s / 10.4s |

scripted 100% 与 live 68.75% 的落差不是退化，而是评测口径切换后的第一份真实测量。
它立即暴露了五类脚本模式永远测不出的失败（见 8.6 节）。其中 tj-005/006 的失败
经 2026-09-19 人工裁决改判为**期望错误**（见 8.6 节末尾），按新口径等效 13/16（81.25%）。

**本地模型基线**（2026-09-19，qwen3:8b via ollama，20 用例，`make eval-trajectory-local`）：

| 指标 | live（本地 qwen3:8b） |
|---|---|
| PassRate | **85.00%**（17/20） |
| ToolAccuracy | 81.82% |
| OrderAccuracy | 50.00% |

失败集中在两个模式：**跳过查重**（tj-007/008，不应再靠提示词加码——
查重是流程确定性要求，应下沉为 `ticket_create_confirm` 后端的强制步骤）
与**混合意图最后一跳**（tj-010）。本地模型的价值：零成本、temp=0 下逐次一致（可作回归基线）、
且可作与被测模型不同源的 judge 候选。

> 运维约束：ollama 默认 4k 上下文即可跑完全部用例；**不要为"保险"调大上下文**——

| prompt token 合计 | 49,130 | 52,491 |

失败用例与旧基线**逐条相同**（tj-007/008 跳过查重、tj-010 混合意图最后一跳），
新增的 tj-021 通过（3 轮 / 2 次工具调用 / `promptTokens=3,361`，
第二轮语义不明确实调了一次模型，且草案仍在等待）。

**⚠️ 一份必须如实说明的读数：旧 20 条用例的 token 与轮次与修复前一字不差。**
这不是"修复没生效"，而是这一轴看不见被修的那个缺陷：
轨迹 runner 直接调 `ag.Run`，不经 `conversation.Service`，客户消息从不落库，
于是历史窗口每条用例都回读到空——跨轮上下文（D1）在本轴的观测里恒为空，
temp=0 下逐 token 一致正好印证了这一点。
而 D2（待确认期间吞消息）需要「草案已挂起 + 下一条消息既非确认也非取消」才会显形，
旧数据集里一条这样的用例都没有：tj-017/018 的第二条是明确取消，
tj-009/010/019 的第二条是明确确认，都由状态机处理，新旧实现走同一条路。
tj-021 是本轴第一条，它同时给 D2（`expectInterrupted` 仍为 true）
与 D3（`expectTicketCreated` 为 false）上了断言。

推论：**D1 目前只有单测与人工对话窗口两处覆盖**（`TestRunSendsHistoryToModel`
与 `eval/samples/manual-*.jsonl`）。要让本轴也能测，需要把 runner 换成经
`conversation.Service.Send` 驱动——那会抬高全部多轮用例的 token 口径，属于独立一次重基线。

**`PassRate` 与 `ToolAccuracy` 必须分开。** 若把工具选择与其他断言混成一个数字，
就无法判断一次退化是「模型选错工具」还是「步骤多了一步」——而这两者的改进方向完全不同。

**延迟用微秒而非毫秒。** 离线评测（脚本化模型 + 内存存储）单轮耗时在微秒级，
毫秒精度下全部取整为 0，指标退化为常量。接入真实模型后数值自然升到数十万微秒，单位不变即可直接比较。

### 3.5 门控阈值是怎么定的（方法论）

置信判定的阈值不能拍脑袋，也不能只看单一阈值下的数字——必须看**两类查询的信号分布**。

实测中先做了一件事：把可回答与不可回答查询的四个候选信号分布画出来。

| 信号 | 可回答中位数 | 不可回答中位数 | 能否区分 |
|---|---|---|---|
| 命中词项数 | **4.00** | **1.00** | ✅ 强 |
| 原始 BM25 分数 | 8.81 | 3.18 | ✅ 强 |
| 归一化分数 | 0.44 | 0.46 | ❌ **完全不可分** |
| 词面覆盖率 | 1.00 | 1.00 | ❌ 无用 |

结论很明确：**归一化分数把信号洗掉了**。原因是它除以「该查询的理论满分」，
短查询会因分母小而虚高——而无关查询往往就是短查询。据此设阈值只能二选一地
牺牲召回或容忍假命中（实测：阈值 0.50 时假命中降到 30%，但可回答判有证据也跌到 28%）。

改用绝对判据（命中词项数 + 原始分数）后：

| 判据组合 | 可回答且有证据 | 假命中率 |
|---|---|---|
| 词项≥2 且 归一化分≥0.30 | 53/80 (66%) | 1/10 |
| **词项≥2 且 原始分≥3.0** | **69/80 (86%)** | **1/10** |

同样的假命中率，召回从 66% 提到 86%。

**过程中修掉的两个自身缺陷**（都由数据暴露，不是靠猜）：

1. **覆盖率对短查询失真** —— 覆盖率是「词表内词项的匹配比例」，
   无关查询里落在词表内的词项本就少，匹配上其中一个就可能是 100%。
   因此加了「命中词项数」这一绝对判据。
2. **误删覆盖率判据** —— 换成绝对判据时我一度把覆盖率的充分性检查也删了，
   单元测试立刻失败。覆盖率能发现「沾到边但没讲到点子上」，
   而相似度判据对此不敏感，因此两条判据独立保留。

### 3.6 真实工单观测（无金标，不是评测）

真实工单没有金标，因此**不计算通过率**——硬塞进轨迹评测只会得到一个没有意义的 100%。
独立命令 `eval-realtickets` 只记录**行为分布**，回答「系统在分布外输入上会怎么表现」。

```bash
python3 eval/gen_realtickets.py /path/to/all_tickets_processed_improved_v3.csv
make eval-realtickets-local                      # 本地 qwen3:8b
```

数据集：GitHub `NajaChandran/IT-Helpdesk-Analysis` 的 47,837 条真实 IT 工单
（8 个类别）按类分层抽样 40 条。CSV 不入库（14MB 且仓库未声明许可证），
只入库抽样结果与生成脚本；原始文本已被上游脱敏（技术名词被 `icon` 等占位符替换）。

**首测结果**（qwen3:8b，2026-09-19，40 条）：

| 指标 | 值 |
|---|---|
| 执行成功率 | 40/40（0 失败、0 越界） |
| 短路率 | 30.0%（12/40） |
| 发起建单确认率 | 57.5%（23/40） |
| 意图分布 | knowledge 18 / incident 10 / out_of_scope 9 / chitchat 3 |
| 延迟 P50 / Max | 28.1s / 57.7s |

两个只有真实数据能暴露的发现：

1. **非技术类工单被礼貌拒答 = 业务丢单**。被短路样本里含大量 HR/行政/采购类真实工单
   （`internal transfer form`、`reallocation of monitor`、`add to...`），系统判为
   `out_of_scope` 后礼貌拒答。而真实语料中 HR Support 占 22.8%、Purchase 占 5.2%——
   这类诉求在真实客服里应当建单或转人工，不该被丢掉。中文构造集覆盖不到这个盲区。
2. **查重跳过在真实数据上更严重**：23 次发起建单确认中只有 6 次（26%）先查重。
   这是第三份数据支持「把查重下沉为后端强制步骤」（前两份是 tj-007/008 的两轮 live）。

> 解读边界：原始文本脱敏严重（`pass pass hi pass activated thanks`），语义残缺，
> 因此部分行为差异应归因于**数据质量**而非系统缺陷。观测结论需与中文评测集交叉印证后
> 才能作为改进依据——上述第 2 点正是两套数据一致，才敢下结论。

## 4. 第二层：归因指标

只有通过率无法指导改进，因此失败原因全部结构化。

### 4.1 检索失败归因（`rag.Reason`）

```
sufficient      证据充分
no_hit          完全没有命中任何片段
low_score       有命中但最高分低于阈值
low_coverage    有命中但未覆盖提问的关键信息
empty_query     提问为空
no_knowledge    未绑定任何知识库
```

**`no_hit` 与 `low_score`/`low_coverage` 的区分是核心价值**：

| 归因 | 含义 | 改进方向 |
|---|---|---|
| `no_hit` | 知识库确实没有这条知识 | **补知识**（知识运营） |
| `low_score` | 词面沾边但语义相关度低 | **换向量模型或调阈值** |
| `low_coverage` | 只沾到边，关键概念未覆盖 | **调召回策略** |

单看向量分数无法区分「知识没覆盖」与「检索没召回」——实测离线向量化器存在偶然哈希碰撞，
无关提问也能拿到 0.16 相似度，会把「该补知识」误报成「该调阈值」。
因此必须引入词面信号作为独立判据。

### 4.2 工具治理拒绝归因（`tooling.ErrorKind`）

```
unknown_tool      工具不存在（模型编造工具名）
not_allowed       不在白名单（配置问题或越权尝试）
budget_exceeded   超出调用次数预算（预算过紧或模型绕路）
args_too_large    参数体过大（模型传了异常大的参数）
invalid_args      参数非法 JSON 或缺少必填项
needs_confirm     写操作待确认
exec_failed       执行期错误
```

`unknown_tool` 指向提示词问题，`budget_exceeded` 指向预算配置问题，二者不可混为一谈。
这正是早期实现把策略拒绝压成一个字符串错误消息的代价——那样无法统计「越权尝试率」。

### 4.3 逐轮成本归因

`agent.TurnResult.RoundRecords` 记录每一轮决策：

```
Round / PromptTokens / CompletionTokens / Tools / DurationUS
```

**这是成本优化的前提。** 真实模型单轮 prompt 可达数千 token，实测数据（优化前，
当时 `ticket_create_draft` 与 `ticket_create_confirm` 尚未合并，故建单占两轮）：

```
第1轮 token=1403/78    工具=[rag_search]
第2轮 token=1655/124   工具=[rag_search rag_search]
第3轮 token=1917/129   工具=[ticket_find_open_by_topic]
第4轮 token=2099/290   工具=[ticket_create_draft]
第5轮 token=2557/222   工具=[ticket_create_confirm]
```

只有分清钱花在哪一轮，才谈得上优化。上表正是「检索质量差 → 模型反复重试 → 成本翻倍」
这一结论的证据来源。

## 5. 第三层：明细记录

### 5.1 单次工具调用审计（`agent.ToolCallRecord`）

```
Code / Risk / Status / ErrorKind / Arguments / Result / DurationMS / DurationUS
```

`Status` 取值：`completed` / `failed` / `awaiting_confirmation` / `rejected`。

### 5.2 工单与指派的完整留痕

- `domain.AssignmentLog`：`Outcome` / **`Reason`（带 `[path=stageN|weakness=...]` 前缀）** /
  `Score` / `Candidates`（含被过滤者及过滤原因）
- `domain.TicketProgress`：按 `Kind` 类型化的进展记录（`created`/`assigned`/`accepted`/`escalated`/`resolved`/`comment`/`dedupe`）

保存候选明细而不只保存结果，是为了让「为什么选了他」可被逐步复核——
能看出胜负是由服务归属决定，还是由负载、资历或边际差决定。
`Reason` 的 path 前缀则保证「这条结论出自哪一段」在事后仍然可查，
否则 Stage 1 直派与 Stage 3 兜底在日志里长得一模一样。

## 6. 与 RAG 评测的衔接

检索与生成质量不在本框架内重复实现。已有的 RAG 评测体系（`MODULAR-RAG-MCP-SERVER`）提供：

| 指标 | 类型 | 说明 |
|---|---|---|
| `hit_rate` | 确定性 | 检索是否命中 |
| `MRR` | 确定性 | 金标排名倒数均值 |
| `faithfulness` | LLM-judge | 答案是否被上下文支撑 |
| `answer_relevancy` | LLM-judge | 答案与提问的相关性 |
| `context_precision` | LLM-judge | 检索片段的排序质量 |

**衔接方式**：agent 侧只需消费 `rag.Reason` 的归因结果做分桶，
文本层指标复用已有实现，避免两套评测各说各话。

二期要补的是**检索轴在本项目的独立报告**：现在检索质量只有单元测试覆盖
（5 个中文提问首位命中 5/5，无关提问正确判 `no_hit`），还没有独立数据集与 Recall@k 报告。

## 7. 评测自身可信度：注入缺陷自证

**指标好看不等于评测评得出问题。** 因此提供 `-sabotage` 注入已知缺陷，
并要求相应指标必须下降：

```bash
make eval-trajectory ARGS="-sabotage=always_write"
```

实测结果（基线 21 条样本，2026-09-23 按交互契约修复后的当前数据集重测）：

| 注入缺陷 | PassRate | ToolAccuracy | 越界率 | AvgRounds | 命中的指标 |
|---|---|---|---|---|---|
| 无（基线） | 100.0% | 100.0% | 0.0% | 1.67 | — |
| `skip_rag` 跳过检索 | 33.3% | **0.0%** | 0.0% | 1.67 | 工具选择 |
| `always_write` 总是建单 | 33.3% | 58.3% | **47.6%** | 1.14 | 安全越界 |
| `extra_rounds` 多余步骤 | 14.3% | 25.0% | 9.5% | **5.67** | 平均轮次 + **预算超限率 100%** |
| `unknown_tool` 编造工具 | 14.3% | **0.0%** | 0.0% | 2.67 | 工具选择 |

> 数据可由 `make eval-trajectory ARGS="-sabotage=..."` 复现。
> 本表按**当前配置与当前数据集**重测（改数据集或 `MaxToolRounds` 后必须重跑，
> 否则表里的数字就成了噪声而非证据）。
> `extra_rounds` 的 AvgRounds 随 `MaxToolRounds` 配置变化
> （该值在 MaxToolRounds=3 时为 4.56，调整为 5 后为 5.56）——
> 这类指标的含义依赖配置，报告时应同时记录配置。
> 与 20 条口径（2026-09-19）对比：四种注入下**原有用例的通过集合逐条未变**
> （7 / 6 / 3 / 3 条），比率变化全部来自分母与新增的 tj-021——
> 这同时是一次「修复没让评测变钝」的自证。

**用例本身也要自证有牙。** 上表四种注入打的是模型脚本，代码侧的锁靠一次变异实验：
临时摘掉 `ParseConfirmationDecision` 的确认否决守卫（`&& !matchesAnyKeyword(value, nonApprovalPhrases)`）
后重跑脚本评测，21 条里**只有 tj-021 失败**，且同时命中两条断言：

```
tj-021 终态中断状态不符：期望 true，实际 false
tj-021 工单创建状态不符：期望 false，实际 true
```

即「我再确认一下……再说」被判成批准并真的建单——正是修复前的行为。
用例不依赖模型配合就能抓到这个回归，这条结论只有变异实验能给出。

**每种缺陷命中不同指标**，证明分轴统计有效。若所有缺陷都只让 PassRate 下降，
说明分轴没有意义，退化时无法定位原因。

**指派轴的注入在单测层，不在 CLI 层**（原先那个对抗数据集随技能层一起删除）。
三个 `TestSabotage_*`（`internal/assign/pipeline_test.go`）用真实构造选项注入已知缺陷，
每个都断言"必须改变结果"，否则测试直接判定该特征不承重：

| 注入 | 手段 | 必须观察到的退化 |
|---|---|---|
| 关闭归属加权 | `WithoutOwnershipBoost()` | 赢家从 owner(11) 翻转走——证明 ownership 是决胜特征而非装饰 |
| 边际阈值归零 | `DefaultPipelineConfig()` + `MarginThreshold = 0` | Stage 2 **不再被触发**，本该升级的样本被 owner 直派 |
| 关闭枚举守卫 | `WithoutLLMEnumGuard()` | 模型编造的 ID 999 被当成 `matched` 采纳，且 `Candidates` 里没有这个人 |

每条都有配对的"守卫生效"测试（如 `TestPipeline_Stage2HallucinationDetected`），
所以这三条不是单向断言，是**同一输入下开关两侧的差异**——与轨迹轴的注入同构，
只是形态是 Go Option 而非命令行开关。代价是它们要改代码才能跑，不像 `-sabotage` 一条命令。

第四类证据较弱但真实：**当前报表本身不是满分**，8 条不一致逐条可归因（金标过期 4 条、
服务解析召回 4 条）。一个只会自证的评测跑不出这种"知道自己哪儿不行"的输出。

## 8. 三个必须声明的解读边界

这三点写进了 README 与 CLI 输出，不接受「看起来很厉害就当作结论」。

**① 指派轴的 85%~93% 不是真实准确率。** v2 数据集的 `goldSource` 写着 `formula-derived`：
金标由派单规则推导，因此三轴证明的是「实现 == 我们宣称的规则」，不是「派单派得准」。
真实准确率需要「工单 → 人工实际指派」的历史数据，排在三期。
在此之前这些数字不得用于任何对外材料——满分与否不改变这个性质，90 分也不比 100 分更"真"。

**② 轨迹评测的 scripted 100% 不是模型能力。** 脚本化模型是「照着期望演」的，
用于验证评测链路与断言正确。测量真实能力用 live 模式：

```bash
LLM_API_KEY=sk-xxx make eval-trajectory ARGS="-json eval/reports/trajectory_live.json"
```

同一套断言、零代码改动，报告标注 `mode: live`。首份实测见 3.4 节与 8.6 节。

**③ 评测不写业务表。** 评测是观察者：业务代码不得 import `internal/eval`，
评测也不得写业务数据。参考实现在这点上踩过坑——评测跑一轮就往生产审计表写行，
污染了「最近 5000 条 run」聚合出的线上 KPI。

## 8.5 成本指标与优化验证

成本既是评测的一轴，也是被优化的对象。固定开销用测试锁进预算，
避免后续新增工具或改提示词时悄悄推高：

```
TestFixedPromptOverheadBudget   固定开销 ≤ 900 token
TestToolCountIsMinimal          工具数 ≤ 3
```

两个上界都由实测确定，不是拍脑袋：优化前固定开销 1,111 token、4 个工具，
测试**正确地失败**并暴露了 `ticket_create_draft` 与 `ticket_create_confirm`
的参数重叠（5 个参数中 4 个相同）。

| 项 | 优化前 | 优化后 |
|---|---|---|
| 系统提示词 | 380 | 332 token |
| 工具 schema | 731（4 工具） | **434（3 工具）** |
| 固定开销 | 1,111 | **766（−31%）** |

真实模型端到端（4 场景）：prompt token 合计 17,591 → **13,034（−26%）**，
建单链路从 5 步降到 4 步。

**方法论价值**：先有逐轮成本归因（第 4.3 节），才能定位固定开销是大头、
并验证优化是否真的生效。没有度量的优化只能靠感觉。

## 8.6 live 首测发现的真实失败模式

首份 live 报告（68.75%）的 5 条失败全部集中在**建单链路**，且模式高度一致——
这正是脚本模式结构性测不出的部分（脚本照期望演，永远不会「忘了建单」）：

| 用例 | 现象 | 归因 |
|---|---|---|
| tj-004 | 只检索未建单，后续「确认」无中断可恢复 | 模型检索无果后未发起建单确认 |
| tj-005/006 | 「帮我建个工单」零工具调用 | 模型选择对话追问信息，而非带 `MissingInfo` 建单 |
| tj-007 | 检索 + 查重都做了，独缺建单确认 | 同 tj-004，链路最后一跳丢失 |
| tj-010 | 检索两次后作答，忽略同一条消息里的「顺便登记」诉求 | 混合意图只处理了主诉求 |

值得注意的反面：**安全越界率 0%**——模型在全部 16 个场景里从未「不该建单却建单」，
错误全部是「该建单没建」（漏做），没有一起「越权做」（多做）。对写操作而言
这是正确的失败分布：漏建可以由追问补回，越权建单是脏数据。

tj-005/006 同时提示数据集自身的问题：「建单不阻塞于信息不全」是**系统**的设计
（`MissingInfo` 机制），但模型天然倾向先追问——期望与产品行为的边界需要人工裁决，
这属于金标口径问题而非模型缺陷。裁决前该两条失败应解读为「待定」而非「错误」。

**2026-09-19 人工裁决结果**：用户仅表达建单意愿而无任何问题描述时，
正确行为是**先追问问题现象**，而非带空描述（`MissingInfo`）直接发起建单确认——
空描述工单对派单与处理没有价值。据此：
- tj-005/006 重写为 `insufficient_info_ask_first` 场景（`ticket_create_confirm` 列入
  `forbiddenTools`），live 首测中模型的「追问」行为从错误改判为正确；
- 原「确认取消」场景覆盖由新增的 tj-017/018 承接（首条消息含问题描述）；
- 系统提示词同步收紧建单边界（有描述→当轮确认；无描述→先追问），期望与提示词两侧同步改。

## 9. 指标与失败模式的对应表

排查问题时按下表定位，这是本文档最实用的部分。

| 观察到的现象 | 查哪个指标 | 可能的根因 |
|---|---|---|
| 用户问题没被解决 | `ToolAccuracy` 低 | 提示词未说清何时该调用工具 |
| 知识库能答的问题却建了单 | `SafetyViolationRate` 升高 | 置信门槛过低，或提示词未强调「先检索」 |
| 出现重复工单 | `OrderAccuracy` 下降 | 模型跳过查重直接建单 |
| 成本突然翻倍 | 逐轮 `RoundRecords` 中某轮 token 异常 | 反复检索/反复改写，检索质量退化 |
| 首轮成本就偏高 | `TestFixedPromptOverheadBudget` | 新增了工具或提示词膨胀 |
| 用户为一个必然失败的操作做确认 | 检查参数校验与确认的先后顺序 | 参数校验被放到了确认之后 |
| 延迟升高但 token 正常 | `Latency.P95` vs `AvgTools` | 单次工具执行变慢（外部依赖） |
| 回复变成「步骤过多」 | `BudgetRejectRate` 升高 | 预算过紧，或模型陷入循环 |
| 声称做了实际没做 | `ToolAccuracy` 正常但 `PassRate` 低 | 模型在回复文本里假装调用了工具 |
| 检索似乎失效 | `rag.Reason` 分桶 | 看 `no_hit`（补知识）还是 `low_score`（改检索） |
