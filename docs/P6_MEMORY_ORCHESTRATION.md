# P6-a 记忆层与拆编排：一次会话之外的东西放哪

复现：`make test`（离线 64 条：`tests/test_ledger.py` 15 + `tests/test_autodream.py` 35 + `tests/test_specialists.py` 14）、
`make probe-p6`（A 段离线挂载与嵌套账、B 段真机三句话 × 两臂成本对照）、`make probe-p6-offline`（只跑 A）、
`make probe-p6-cron`（真机心跳：把 cron 换成每分钟，等两次触发，约 3 分钟）。

## 根因：托管路径没有任何跨会话的业务事实

`make_service_app` 的 `ctx_for` 是按 `session_id` 建上下文的 —— 工单簿、预约簿都跟着会话生，
而框架持久化的是 sessions 与 `AgentState`（"模型记得建过单"），不是业务事实（"系统里有这张单"）。
所以"长期偏好""行为分析"这些说法在这条路径上原本**没有可读之处**：
先要有一层按用户而不是按会话落的事实源，才谈得上折它。这就是 `ledger.py` 存在的唯一理由。

三件套各有其因，缺一个就会长出很难查的错：

| 件 | 在哪 | 缺了会怎样 |
|---|---|---|
| 原始事实（追加式 JSONL） | `ledger.py` | 只有派生表 → 结论不可重算，改一次折规则就得从头再折一遍 |
| 检查点（`Counters.seq` = 行号） | `memory.py` | 每轮从头重算 → 计数指数膨胀；有它，崩在落盘之前重跑等于没跑过 |
| 任务锁（`flock`，`LOCK_NB` 不自旋） | `ledger.lock()` | 折叠是"读表→改→整表写回"，两台交错就把同一批行折两次；拿不到就跳过这一轮，cron 还会再来 |

## 事实源的形状：行映射归适配器，不归簿

`ticket_sink` / `appointment_sink` 住在 `ledger.py`，因为"一行进展折成几个事实"是**读法**的一部分：

- `missing` 是快照，每条进展行都重复一遍（那字段本来就是 write-once）。折叠只数 `ticket.created` ——
  不是因为只有那里读得到，是因为读五条会把一次缺失算成五遍。
- 写穿用**变更时刻**（`event.at`）而不是 `datetime.now()`：补记的历史会把时段分布折歪。
- `改期` 不折成第二次偏好（同一趟上门算两次会污染"常约几点"）。
- 撕裂的**最后一行**静默丢弃（写一半被断电是常态），**中间**坏行当场 `ValueError` ——
  报的是日志里的行号，不是内存下标。
- `seq` 由写方自己取（`append()` 先取号再写），但**权威行号在回放时重算**：多写者交错时
  自己那个号只是自己的视图，检查点认的是文件里的位置。

## 派生表：每个结论都带着它是多弱

`memory.py` 折成 `Counters`（表）→ `summarize` 出 `Preferences`（视图）。措辞上强制带样本数：
`- 上门时段：上午 3/5 次`、`依据：5 张工单 / 5 次预约`；并列**不算**偏好（`_plurality` 平了返回 None）；
两个率各有各的分母 —— 完成率的分母是"真的上过门"（约了没来的既不算完成也不算失败），
取消率的分母是"约成的次数"（还挂着没履约的与它无关）。空表说的是
"没有历史记录（第一次接触这位用户）。别拿假设当偏好。"

读它的工具是 `recall_preferences`（只读、ALLOW、永远注册）。系统提示词给它划了界：
**只在用户于几个时刻之间犹豫时当参考样本，不能替用户决定，也不要把数字念给用户听。**

`run_autodream` 反过来 —— 它**只在挂了落盘事实源的上下文里注册**。console / 单测 / 评测里没有日志，
递交一个永远回 `not_wired` 的工具只会多烧一轮。

## 接调度器：为什么不是自己起一个 asyncio 循环

框架的调度器把定时器、**多节点归属**（只有一台持有 timer，storage 才是事实源）、misfire 宽限、
以及"这一轮跑在哪个 session、事件流看不看得见"一并给了。重写这些正是"原生优先"要避免的事。
代价写在同一条线上：每次触发要多花一轮模型调用，而调度器只能递给 agent 一段 `description` 文本
（`AUTODREAM_PROMPT`），所以"做什么"必须长在工具里，模型的活儿只是把它调一次。

四条只有接上去才知道的接缝：

1. **`permission_mode=DONT_ASK` 是物理保证，不是提醒。** 该模式把每一条 ASK 换成 DENY
   （`permission/_types.py`）。所以无人看管的这一轮里 `create_ticket` / `book_appointment`
   根本执行不了 —— 这正是我们要的形状，靠提示词写"别建单"是另一回事。
2. **于是 `run_autodream` 必须是 ALLOW。** 它要确认就等于 AutoDream 永远跑不了
   （DENY 掉的是它自己）。`test_整理工具必须是可以直接跑的` 钉的就是这条，不钉的话整个功能会静默死掉。
3. **`enable_scheduler` 原本关着**（`create_app(enable_scheduler=False)` 是我们的默认）。
   打开它才有 timer；而框架白送的 `ScheduleCreate/ScheduleList` 那些工具**不在工具面白名单里** ——
   让模型给自己加 cron，等于把"什么时候能醒"交给提示词。
4. **注册按 name 收敛，不按 id**（id 每次新生成，重启一次堆一条 cron 等于每天醒很多遍）。
   但不是"有同名就跳过"：跳过等于把改动永久留在家里 —— 那条 `force=false` 的措辞修正
   （见下面"真机心跳"）就永远到不了已经登记过的部署。现在比的是**这个进程想写的那几个字段**
   （cron / timezone / description / chat_model_config / agent_id，外加 permission_mode 与
   stateful 这两条安全边界），一致就一字不动，不一致就原地刷同一条记录。
   `enabled` 不在名单里：人把调度关掉是熔断，不该每次启动都替他打开。
   写入形状照 `ScheduleCreate.__call__`：`validate_schedule` 先验 cron（坏表达式在落库**之前**被拦下）
   → `upsert_schedule` → `notify_changed` 提醒持有 timer 的那个节点来 reconcile。
   `stateful=False`：每次醒来都是一个新 session，整理不该被当成"上次对话的继续"。

闸的三条理由分开报（`test_三条理由彼此分开`）：没有新事实 / 间隔不足 / 会话数不足 ——
混成一条"不该跑"就没法判断是闸门坏了还是没有料。
**会话数从待折的行里数，不从计数表里数**：计数表只在跑成功之后更新，拿它当闸门是
"要等它非空才肯跑，而它只有跑过才非空"的死锁。

## 真机心跳：把 cron 临时调到每分钟，看它到底醒不醒

上面那些都是线下的账。"到点真的醒一次、并把 `run_autodream` 调起来"这一环只能真跑，
而默认 cron 是凌晨三点 —— 所以 `probes/p6_autodream_cron.py`（`make probe-p6-cron`）
把心跳换成 `* * * * *`，在一个一次性世界（`mkdtemp` 里的服务库/工作区/记忆目录 + 复制的向量库）
里等两次分钟边界。**改产的只有周期**：登记走桥 first-ready、触发走 `SchedulerManager._trigger`、
执行走 `WakeupDispatcher → ChatService.run`，一处都没替。

五条判据（2026-09-27 20:47 / 20:50 / 20:56 三跑全过，退出码 0；后两跑的是改过提示词与
注册收敛之后的代码）：

| | 判据 | 机器上读到的 |
|---|---|---|
| C1 | 登记 | 调度存储恰好 1 条 `autodream`，`permission=dont_ask`、`stateful=False`、model 与前台同 |
| C2 | 落地 | 分钟边界后 `list_sessions_by_schedule` 出现新 session（距启动 66–120s，看注册落在分钟内哪一秒） |
| C3 | 执行 | 那一轮 `run_autodream` 的 tool_result 正文 = `DreamResult.text()`，检查点 0→15 |
| C4 | 闸 | 第二次心跳照样醒、照样调工具，正文 `AutoDream 本轮没跑：…`，`runs` 仍是 1 |
| C5 | 不写 | 日志行数 15→15，无人值守那几轮没往事实源里添过一行 |

一次触发的价钱：**in 7507–7660、out 26–142 token**（`Msg.usage` 按轮累计；out 的跨度就是
"读的那一刻收尾文本落没落库"，同一句话逐字稳定这条在 P1 记过）。
C4 那条是这一节最想留的东西 —— "cron 是心跳、真正的条件是那两道闸"在此之前只是注释里的说法。

真跑带回来两个只有真跑才暴露的东西：

1. **模型自己传了 `force=true`**（两次心跳都是 `run_autodream({"force": true})`，20:43 那一跑）。
   提示词说的是"立刻调用一次"，它读成了"强制调用"。`force` 正是那两道闸的旁路，
   于是每天凌晨的自动整理会**静默绕过**"新会话满 5 次 / 距上次满 24 小时"。
   调度器递得过来的只有 `description` 那一段文本，所以修法只能写进文本：
   `AUTODREAM_PROMPT` 现在明说"force 参数留空（也就是 false）"，改完再跑，两次心跳都传 `false` 了。
2. **`force` 遇上空批会崩**：`run()` 里检查点要推到 `rows[-1]`，而 `force` 把"没有新事实"
   那条也跳过了 → `IndexError`，框架把异常字符串原样当工具正文回给模型
   （那一轮模型读到的是 `list index out of range`）。修法在 `autodream.run()`
   —— force 跳阈值、不跳"无米之炊"，返回 `ran=False` 带一句能看懂的理由；
   钉在 `test_没东西可折时force也不许把检查点推到空批`。

第 2 条的形状值得记一句：**工具崩了不会响，只会变成模型手里一句读不懂的话。**
所以这条探针的判据是"正文必须以 `AutoDream：` 开头"，而不是"这一轮没报错"。

## 滚动摘要：0.6，且只有一份配置

框架默认 `trigger_ratio=0.8` 等于贴着上限才压 —— 长会话里最后一轮工具结果就能把上下文顶穿。
改成 0.6，且 `CONTEXT_CONFIG` 是同一份阈值的两种形状（console 吃 `ContextConfig` 对象，
托管路径吃 `POST /agent/` 的 JSON），两份配置迟早漂。

## 拆编排：量具先上，结论是"别开"

`specialists.py` 把咨询/预约/派单三步包成三个工具（进程内 `Agent` + `FunctionTool`，
不是框架的 `SubAgentTemplate` —— 那是"把活扔进另一个会话"，业务要的是"主管一次推理里问一句、马上拿到答案"）。
三条约束：专线里不能有需要确认的写工具（子流的 `RequireUserConfirmEvent` 没人能回答，整条链挂死）；
嵌套的模型调用在外层事件流里**看不见**，所以 `_run` 把子流的 `ModelCallEndEvent` 聚进 metadata；
共享的是业务事实和用户原话，不是同一个 `AgentState` 对象。

真机实测（`qwen3:8b` temp=0，`probes/p6_specialists_cost.py`，2026-09-27 20:20 / 20:26 两轮，每格 2 个样本）：

| 场景 | 关臂 token | 开臂 token | Δ | 两臂实际走的路 | 专线被调用 |
|---|---|---|---|---|---|
| `consult` 明确要求查知识库 | 5858 | 6366 | **+508** | `search_knowledge` → 收尾（两臂 out 都是 100） | 0 |
| `intake` P3 的 short | 3892 | 4313 | +421 | `ask_user` → 收尾（out 64 → 154，混了措辞漂移） | 0 |
| `visit` 点名要约上门 | 3814 | 4098 / 4097 | +284 / +283 | `ask_user` → 收尾 | 0 |

结论按最干净的那一格读：`consult` 两臂轨迹与输出 token 完全相同，+508 就是**纯工具面变宽的代价**
—— 三个 schema 999 字 ≈ 每次调用 +254 token × 2 次调用。12 次真机轮里 `advise_dispatch`
`consult_ticket` `plan_visit` 一次都没被选中，包括 `visit` 那一格（"直接调 `propose_appointments`"
和"交给专线"两条路都走得通，模型每次都选了前者）。
**所以 `HELPDESK_SPECIALISTS` 保持默认 0**：这层现在的净效果是每轮多烧 250 token 换一个模型不用的抽象。
量具留着（`NestedUsage` 那条聚合是这条路线唯一确定的产出 —— 它证明外层事件确实少算，A3 离线钉死：
外层 1 次工具调用 = 内层 2 轮模型、870 token）。要继续推它，得先解决"8B 模型不选它"，
而那需要先验：主管提示词显式点名专线（等于承认拆编排还要另付提示词成本），或者给专线单独出题集。

顺带一条对"temp=0 可复现"的收紧观测：同一句话的**输入**侧 token 逐字稳定
（3828/3828、5758/5758、3777/3777），漂的是**输出**（visit 那一格 51 vs 50 token），
而输出一漂、下一轮的输入就跟着漂 —— P1 那条"temp=0 仍不可复现"的机制在这里看得见形状。

## 已知边界（没做的，都写清楚）

- **JD 那套 0.6/0.3/0.1 加权召回没做。** 三个权重是三个待估参数，没有消融就写进代码等于把一个
  编出来的常数当架构。现在的召回只有一路 dense，偏好表是**读**出来给模型的，不参与打分融合。
- cron 登记挂在**桥第一次就绪**（`AguiBridge.on_ready`），不是进程启动：那时才拿得到 `agent_id`
  与 `chat_model_config`。所以 `make serve` 之后没人访问 `/ag-ui`，AutoDream 的 cron 就还没登记。
- **改 `SYSTEM_PROMPT` 不会自动生效**：桥对已存在的 agent 只读不写，要改得重建 agent 行。
- cron 触发已在机器上验过，但验的是**替换过的周期**（`* * * * *`）：出厂默认 `0 3 * * *`
  没有守过一整夜，也没验过多节点归属（只有一台进程，timer 归谁这条是框架的说法）
  与 misfire 宽限（机器睡着了醒来补不补）。
- `pending` 与 `_threads` 在进程内（P5 那条边界没变），服务重启后旧卡片答不了。
- 折叠是**全量重算派生表**（读增量行、改表、整表写回），没有 tombstone：日志里写错一行，
  只能靠重放修正，删不掉已折进去的计数。
- 多用户只有 `HELPDESK_USER` 一个身份（本机单人测试），一份日志/一张表 per user 的形状对，但没验过两户。
