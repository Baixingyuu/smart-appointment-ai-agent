### 2.1 自研 bounded loop（简历点：Agent loop 设计）

**决策：不用 Eino，也不用 LangChain AgentExecutor，自研约 250 行。**

理由（一期已积累实证）：agent-desk 用 Eino 的代价是 token 记账不完整（只取最后一次 model 调用的 usage，多步工具调用下成本被系统性低估）、trace 与 loop 内部状态脱节、评测拿不到 suppress 前的决策。框架会把关键信号藏在内部。

**Loop 契约**

```
输入：system_prompt, user_message, tools[], budgets
循环：for step in 0..max_steps:
        决策 = LLM(system, messages, tools)      # 单次调用，非 ReAct 多轮文本
        if 终态: 写 trace, 返回
        if 工具调用:
            授权（分级 / 白名单 / 预算 / 参数大小）  # 拒绝也要落 trace
            if 需确认: 写 interrupt, 返回
            执行 → 写 trace
输出：reply_text, trace_id, tokens{prompt,completion}, total_duration_ms
```

**必须做到的四件事**（都是一期已有的 schema，二期只需正确填充）

| 项 | 要求 |
|---|---|
| 预算 | `max_steps` / `max_total_tool_calls` / `max_argument_bytes` 三重 |
| 分级 | `read` / `write`，write 必经确认 |
| token | **全步累加**，不是只取最后一步 |
| trace | ~~`Surface` 字段记录模型是包装调用还是直连~~ → **未实现，且前提已变**：`tool_search` 包装方案从未落地，现在只有 3 个直连注册工具，没有"调用面"可区分。实交付的轨迹 schema 是 `RoundRecord` + `ToolCallRecord`（Code / Risk / Status / ErrorKind / Arguments / Result / DurationMS / DurationUS） |

**新增评测轴**：工具选择准确率（有序/无序）、工具冗余率、平均步数偏差、预算超限率、越权尝试率。

### 2.2 Agentic RAG（简历点：Agentic RAG）

一期是单轮检索。二期加**决策循环**：

```
for round in 0..max_rounds(2):
    hits = retrieve(query)
    sufficient, reason = evidence_gate(hits)
    if sufficient: break
    query = rewrite(query, hits, reason)     # 用已有 hit 反推缺什么
if 始终不充分: 按 fallback_mode 降级（追问 / 转人工 / 明确说明知识不足）
```

**`evidence_gate` 的判定维度**（与参考实现的差异点）

| 维度 | 判据 | 参考实现（agent-desk） |
|---|---|---|
| 召回存在性 | `len(hits) > 0` | 只做到这里 |
| 置信充分性 | `top_score >= threshold` | 新增 |
| 覆盖充分性 | 命中覆盖 query 关键实体比例 | 新增 |
| 冗余抑制 | 单文档 ≤2 条、同章节去重 | 已有 |
| **失败归因** | `reason` 区分 `no_hit` / `low_score` / `low_coverage` | 新增 ★ |

**为什么 `reason` 是关键**：它能区分「知识库没覆盖」与「检索没召回」——这是两条完全不同的改进方向。判空式的 gate 产生不了这个区分。一期已落库 `reason`，二期扩展枚举值。

**新增评测轴**：召回率、MRR、按 reason 分桶的失败分布、平均检索轮次、忠实度（Faithfulness）。

忠实度评测需 Python 侧车（Ragas 或自写 LLM-judge），采用**子进程 + JSON 契约**，不做常驻服务。

### 2.3 MCP 抽象（按需，可延后）

**建议：二期先做工具抽象层，MCP 协议落地按需。**

- 一期的 4 个工具在进程内，引入 MCP 等于为解耦而解耦
- MCP 的价值在**工具提供方解耦**，服务于第三方系统接入
- 二期的工具注册表已按统一 schema 设计，将来替换为 MCP 协议**不改业务代码**

**若接入 MCP，优先级顺序**：
1. 通知渠道（Webhook / 企业微信）——真正的外部系统，包装成 MCP tool 有意义
2. 日历 / 排期（如需要）
3. 第三方工单系统同步

### 2.4 二期验收标准

- [ ] Loop 全步 token 累加，与上游 provider 账单可对账（误差 <5%）
- [ ] 每次工具调用都有真实步级耗时（不出现整轮时长充当步时长）
- [ ] 策略拒绝、预算超限、参数超限全部落 trace，带结构化 `ErrorKind`
- [ ] Agentic RAG 在固定测试集上检索轮次 ≤2，且失败可归因到 reason
- [ ] 工具选择准确率相对一期提升有量化对比

## 三期：学习与闭环

> **微调**与**用户行为分析**两个简历点在本期完成，同时把手工维护的**服务归属字典**演进为自动画像
> （原计划的"人工技能标签"已于 2026-09-24 删除，不再是演进对象）。

### 3.1 微调（简历点）

**推荐做两个任务，主战场放在行为分类。**

| 任务 | 数据 | 为什么 |
|---|---|---|
| **主：用户行为分类**（流失 / 升级预测） | 行为事件自动生产，**无需人工标注** | 有真标签、数据量易堆、小模型优势明确、微调收益易证明 |
| 次：工单信息抽取 | 需人工金标 ≥400 条 | 覆盖「信息提取」表述 |

**为什么把主战场从抽取换成行为分类**：抽取微调有天然弱点——prompt + schema 校验往往就能达到不错效果，微调收益不易证明（回滚条款：F1 提升 <3pt 则该任务作废）。而行为分类是天然分类任务，标注成本低一个数量级。

**抽取任务的关键设计：用 schema 强校验替代 prompt 里写「只输出纯JSON」。**

一期现状（继承自 `smart-appointment`）的脆弱性：靠提示词约束 JSON，评测脚本要手写 `priority[:2]` 截断 LLM 自由输出。这个脆弱性本身就是微调任务的动机，也是面试可讲的「问题定义」。

**三向对照实验（简历数字来源）**

| 方案 | 字段 F1 | schema 合规率 | P50 延迟 | 单次成本 |
|---|---|---|---|---|
| B1 prompt-only（一期现状） | 基线 | 基线（低） | 基线 | 基线 |
| B2 + schema 校验 | ↑ | ↑ | 不变 | 不变 |
| B3 LoRA 微调 | ↑↑ | ↑↑ | **显著↓** | **显著↓** |

**数据构造**：输入分布用 agent-desk 真实中文客服语料；金标来自人工修正工单；字段定义沿用 `smart-appointment` 的 `InputParser`。划分 train/dev/test = 6:2:2，**test 集冻结，只在最终报告使用**。

### 3.2 用户行为分析（简历点）

**必须承认的基线事实**：两个参考仓库的「行为分析」本质都是**频次统计**——上游 `preference_manager` 的「学习」是 `confidence_score += 1`（纯计数，无时间衰减、无平滑），`pattern_analyzer` 是频次取 `max()`。仅搬运会被问倒：「这和 SQL 的 GROUP BY 有什么区别？」

**因此三期要补真算法**：

| 能力 | 方法 | 说明 |
|---|---|---|
| 偏好时间衰减 | 指数衰减权重替代 `+=1` | 一行公式，可解释 |
| **意图漂移** | 近30天 vs 前30天意图分布 **JS 散度** | 有明确数学定义，可复现 |
| 流失/升级分类 | 行为特征 → 轻量分类器 | 与 3.1 主任务合流 |
| **自动归属画像** | 从历史工单统计「谁真正解决过哪个服务」 | **替代手工维护的 `Service` owner/backup 列表与 `EmployeeExtension`**（原「自动技能画像替代人工技能标签」，技能层已删） |

**意图漂移是本项目独有优势**：二期 loop 每轮都往 trace 落 `DecisionAction` 与路由意图，**意图序列是免费副产品**。这是「自研 loop + 统一 trace」这个设计决策的自然收益，能讲成完整因果链。

**行为分析的分工原则**：规则算分 + LLM 只组织文案。分数若由 LLM 生成则不可复现、不可回归测试、无法向业务解释。

### 3.3 知识闭环

| 工作项 | 价值 |
|---|---|
| 工单解决方案回写知识库 | 降低后续同类工单量（真实客服系统最易漏、价值最高的一环） |
| 同类问题聚类 → 知识运营工单 | 把重复问题转化为知识建设任务 |
| 关闭原因 → 解决码统计 | 质量分析基础 |

### 3.4 三期验收标准

- [ ] 抽取任务有 B1/B2/B3 三向对照数据，样本量 ≥400 且 test 集冻结
- [ ] 行为分类有明确基线（规则阈值）与量化提升
- [ ] 意图漂移在合成案例上可验证（构造分布迁移，断言漂移值上升）
- [ ] 自动归属画像与手工维护的服务字典/员工扩展对比，报告一致率（原「与人工技能标签对比」，该层已删）
- [ ] 知识回写后，同类工单量的下降有前后对比

### 贯穿三期的红线

- **样本量不足就写样本量不足，不伪造数字。** 这是面试里唯一会被真正否定的事。
