# 分阶段路线图（Phase Roadmap）

> **命名说明**：文中 `agent-desk` 指上游**参考仓库**（`../agent-desk`），
> 本项目名为 **`helpdesk-agent`**。

> 配套文档：`FUSION_DESIGN.md`（架构与 ADR 决策）
> 本文档是**分期实施的权威依据**，取代同目录 `FUSION_DESIGN.md` 第 7~9 节的 M0–M6 试验性排期。
> 状态：一期未动工。

---

## 0. 分期总览

| 期次 | 主题 | 对应简历点 | 核心新增 | 量化产出 |
|---|---|---|---|---|
| **一期** | 工单落地场景 | 系统评测（部分） | 技能标签体系 + 确定性派单器 | 路由 / 指派 / 召回 准确率 |
| **二期** | 多步决策能力 | Agent loop 设计、Agentic RAG | 自研 bounded loop + 检索决策循环 | 工具选择准确率、平均步数、检索轮次 |
| **三期** | 学习与闭环 | 微调、用户行为分析 | LoRA 抽取 + 行为分类 + 知识回写 | 字段 F1、schema 合规率、延迟与成本降幅 |

### 依赖关系（必须按序）

```
一期：会话 → RAG(单轮) → 工单 → 【技能标签 + 派单】
                                    │
                                    │ 派单准确率需要评测框架
                                    ▼
                              【评测框架（一期内建）】
                                    │
二期：自研 bounded loop ────────────┤ 评测已有 trace 可消费
      Agentic RAG（改写重检索）─────┤ 检索 reason 分桶可复用
      MCP 抽象（按需）──────────────┘
                                    │
三期：微调抽取 ─────────────────────┤ 需要派单留下的工单语料
      行为分析 ────────────────────┤ 需要一期的行为事件表
      自动技能画像（替代人工标签）──┘ 需要二期积累的工单-人 配对
```

**为什么一期必须先做**：派单准确率是三个期次里唯一能在**没有 LLM 参与**的前提下量化的指标（确定性匹配）。它同时为一期建立评测基准、为三期积累「工单 → 处理人」的配对数据。二期、三期都消费一期的产出。

## 一期：工单落地场景

### 一期目标

打通「咨询 → 检索 → 建单 → 派给有经验的员工 → 处理 → 关闭」全链路，且**可评测、可解释、可审计**。

### 一期内明确不做

| 不做 | 归入 |
|---|---|
| RAG 查询改写与多轮重检索 | 二期 |
| 自研 agent loop / 多步工具编排 | 二期 |
| MCP 协议接入 | 二期（按需） |
| 微调（抽取 / 行为分类） | 三期 |
| 用户行为分析与偏好学习 | 三期 |
| 前端界面（用 CLI + 评测 CSV 替代） | 不排期 |
| 多租户 / RBAC / 组织管理 | 不排期 |

### 1.1 工作项

**A. 会话与消息（复用）**
- 会话创建、消息落库、AI 回复写入
- 老用户识别 → 加载历史工单与偏好摘要（进入 Prompt 上下文）

**B. 单轮 RAG + 真置信判定**
- 检索底座：TopK / ScoreThreshold / ContextMaxTokens 参数化
- **把 agent-desk 的伪 gate（判空）替换为真置信判定**
- 置信不足时走降级策略，并记录 `reason`（`no_hit` / `low_score`）

> 注：多轮改写留到二期，但 `reason` 字段一期就要落库，二期直接复用做分桶归因。

**C. 工单全链路**
1. 去重检查：同用户 7 天内同类未关闭工单 → 追加进展而非新建
2. 信息补全：缺 `description` 时先追问；问不清也建单并标记 `missing_info`
3. 字段填充：`title` / `description` / `category` / `priority` / 来源会话 / 标签
4. HITL 确认（写操作必须确认）
5. 事务落库：工单 + 标签 + 进展 + 事件
6. 幂等保护：`(ConversationID, ToolCode, IdempotencyKey)` 唯一约束

**D. 技能标签体系（一期新增主体之一）**

**采用方案 A：标签即技能。**

- 技能树：`Tag.ParentID` 建层级（如 `技能根 → 网络 → 接口 / 性能`），**零迁移成本**
- 员工侧：给 `AgentProfile` 关联技能标签
- 工单侧：`category` + 标签即技能需求向量

> 方案 B（LLM 打分）明确不用：会让「指派准确率」失去意义，无法区分是算法还是模型发挥。
> 方案 C（自动画像）三期做，替代人工维护标签。

**E. 确定性派单器（一期新增主体之二）**

```
输入：工单技能向量 + 处理人技能向量 + 负载状态
① 候选过滤：状态可用 ∧ 技能标签命中 ∧ 未达 MaxConcurrentCount
② 候选排序：专长匹配度(Jaccard) > 当前负载 > 最近响应时长
③ 兜底：无命中 → 值班人 / 待认领池
④ 记录指派理由 → TicketAssignmentLog
```

- 匹配度用 **Jaccard 相似度**（`smart-appointment` 的 `EngineerFinder` 已有参考实现）
- **指派理由必须落库**，这是「可解释」与「可评测」的前提
- 派单在后端服务层，**不做成模型工具**（模型不参与派单决策）

**F. 工单状态流转**
- `pending → in_progress → done` 流转规则
- 补齐 `in_progress` 自动置位（agent-desk 从不自动设置）
- 二次无解 → 升级（换人 / 升级资深 / 转负责人）
- 状态变更写进展记录（agent-desk 现状：状态变更不写进展，无法审计）

**G. 工具与治理（模型侧仅 4 个工具）**

| 工具 | 类型 | 说明 |
|---|---|---|
| `rag.search` | 读 | 检索知识库，返回带 score 的证据 |
| `ticket.find_open_by_topic` | 读 | 去重检查 |
| `ticket.create_draft` | 读 | 生成草稿，不写库 |
| `ticket.create_confirm` | **写** | HITL 确认后写库 |

治理要素：工具分级（read/write）、三重预算（最大调用数 / 参数大小 / 允许风险级）、确认中断、幂等。

**H. 数据模型最小补充**

| 新增 | 用途 | 谁填 |
|---|---|---|
| `Ticket.Priority`（P0–P3） | 派单排序、SLA | **规则计算，不让模型预测** |
| `Ticket.CategoryID` | 技能匹配主键 | 规则 + 标签推导 |
| 员工技能标签关联 | 方案 A 的基础 | 复用 `Tag`，零迁移 |
| `TicketAssignmentLog` | 指派理由、评测与审计 | 派单器 |

> `Priority` 用确定性规则算的理由：直接影响 SLA 与派单顺序，模型决定会导致不可复现、难向业务解释。规则可直接移植 agent-desk 已有的中文关键词信号（`analyze_conversation_graph.go` 的 `financial_risk` / `complaint_escalation` 与 `deriveRiskLevel`）。

**I. 评测（一期内建，本期的核心交付之一）**

| 轴 | 指标 | 数据集 |
|---|---|---|
| 路由 | Accuracy、Macro-F1、按类混淆矩阵 | 意图 ≥200 条 |
| **指派** | **Top-1 命中率、MRR、无命中率** | **工单 → 金标处理人 ≥100 条** |
| 检索 | Recall@k、MRR、`gate` reason 分桶 | RAG QA ≥100 条（带金标片段） |
| 轨迹 | 工具调用序列、步数、token、延迟 | ≥50 条 |

- 含**规则基线**做对照（零 API 成本）
- 报告输出 JSON（机读回归）+ CSV（人读）
- **修正 `smart-appointment` 的 `top_k_accuracy`**：现实现忽略 `k`，只做逐元素比较
- 评测与业务 trace 表**物理隔离**（修掉 agent-desk 评测污染生产 KPI 的缺陷）

**J. CLI**

```
make init          建库 + 迁移 + 种子
make seed          生成技能标签树、员工技能、FAQ、历史工单
make run           启动服务
make eval          跑评测（路由/指派/检索/轨迹）
make eval-report   导出 JSON + CSV
make tickets-review  人工核对指派结果（构造金标）
make doctor        环境自检
```

### 1.2 一期验收标准

- [ ] 全链路可跑通：一句话咨询 → 建单 → 自动派到合适员工 → 关闭
- [ ] 派单结果**确定性可复现**（同一输入同一输出），且有单元测试覆盖
- [ ] 每次指派都留下可读理由，业务方可复核
- [ ] 4 个模型侧工具全部经过治理层（分级 / 预算 / 确认 / 幂等）
- [ ] 评测框架产出四轴报告，且**含规则基线对照**
- [ ] 评测**不写入**业务 trace 表

### 1.3 一期可写入简历的数字

- 指派 Top-1 命中率 **X%**（对比随机基线 **Y%**）
- 去重拦截率、工单自动创建成功率
- 检索 Recall@k、置信不足误判率

> 一期所有数字都不依赖 LLM，因此**可复现**——这本身就是「评测体系」这条简历点的可信度基础。

## 二期：多步决策能力

> **Agent loop 设计**与 **Agentic RAG** 两个简历点在本期完成。
> 一期已把工具治理、trace schema、评测框架建好，二期是在此基础上**替换决策内核**，不是重写。

### 2.1 自研 bounded loop（简历点：Agent loop 设计）

**决策：不用 Eino，也不用 LangChain AgentExecutor，自研约 250 行。**

理由（一期已积累实证）：agent-desk 用 Eino 的代价是 token 记账不完整（只取最后一次 model 调用的 usage，多步工具调用下成本被系统性低估）、trace 与 loop 内部状态脱节、评测拿不到 suppress 前的决策。框架会把关键信号藏在内部。

**Loop 契约**

```
输入：system_prompt, user_message, tools[], budgets
循环：for step in 0..max_steps:
        决策 = LLM(system, messages, tools)      # 单次调用，非 ReAct 多轮文本
        if 终态: 写 trace, 返回
        if 工具调用:
            授权（分级 / 白名单 / 预算 / 参数大小）  # 拒绝也要落 trace
            if 需确认: 写 interrupt, 返回
            执行 → 写 trace
输出：reply_text, trace_id, tokens{prompt,completion}, total_duration_ms
```

**必须做到的四件事**（都是一期已有的 schema，二期只需正确填充）

| 项 | 要求 |
|---|---|
| 预算 | `max_steps` / `max_total_tool_calls` / `max_argument_bytes` 三重 |
| 分级 | `read` / `write`，write 必经确认 |
| token | **全步累加**，不是只取最后一步 |
| trace | `Surface` 字段记录模型是包装调用还是直连（区分调用面） |

**新增评测轴**：工具选择准确率（有序/无序）、工具冗余率、平均步数偏差、预算超限率、越权尝试率。

### 2.2 Agentic RAG（简历点：Agentic RAG）

一期是单轮检索。二期加**决策循环**：

```
for round in 0..max_rounds(2):
    hits = retrieve(query)
    sufficient, reason = evidence_gate(hits)
    if sufficient: break
    query = rewrite(query, hits, reason)     # 用已有 hit 反推缺什么
if 始终不充分: 按 fallback_mode 降级（追问 / 转人工 / 明确说明知识不足）
```

**`evidence_gate` 的判定维度**（与参考实现的差异点）

| 维度 | 判据 | 参考实现（agent-desk） |
|---|---|---|
| 召回存在性 | `len(hits) > 0` | 只做到这里 |
| 置信充分性 | `top_score >= threshold` | 新增 |
| 覆盖充分性 | 命中覆盖 query 关键实体比例 | 新增 |
| 冗余抑制 | 单文档 ≤2 条、同章节去重 | 已有 |
| **失败归因** | `reason` 区分 `no_hit` / `low_score` / `low_coverage` | 新增 ★ |

**为什么 `reason` 是关键**：它能区分「知识库没覆盖」与「检索没召回」——这是两条完全不同的改进方向。判空式的 gate 产生不了这个区分。一期已落库 `reason`，二期扩展枚举值。

**新增评测轴**：召回率、MRR、按 reason 分桶的失败分布、平均检索轮次、忠实度（Faithfulness）。

忠实度评测需 Python 侧车（Ragas 或自写 LLM-judge），采用**子进程 + JSON 契约**，不做常驻服务。

### 2.3 MCP 抽象（按需，可延后）

**建议：二期先做工具抽象层，MCP 协议落地按需。**

- 一期的 4 个工具在进程内，引入 MCP 等于为解耦而解耦
- MCP 的价值在**工具提供方解耦**，服务于第三方系统接入
- 二期的工具注册表已按统一 schema 设计，将来替换为 MCP 协议**不改业务代码**

**若接入 MCP，优先级顺序**：
1. 通知渠道（Webhook / 企业微信）——真正的外部系统，包装成 MCP tool 有意义
2. 日历 / 排期（如需要）
3. 第三方工单系统同步

### 2.4 二期验收标准

- [ ] Loop 全步 token 累加，与上游 provider 账单可对账（误差 <5%）
- [ ] 每次工具调用都有真实步级耗时（不出现整轮时长充当步时长）
- [ ] 策略拒绝、预算超限、参数超限全部落 trace，带结构化 `ErrorKind`
- [ ] Agentic RAG 在固定测试集上检索轮次 ≤2，且失败可归因到 reason
- [ ] 工具选择准确率相对一期提升有量化对比

## 三期：学习与闭环

> **微调**与**用户行为分析**两个简历点在本期完成，同时把一期的人工技能标签演进为自动画像。

### 3.1 微调（简历点）

**推荐做两个任务，主战场放在行为分类。**

| 任务 | 数据 | 为什么 |
|---|---|---|
| **主：用户行为分类**（流失 / 升级预测） | 行为事件自动生产，**无需人工标注** | 有真标签、数据量易堆、小模型优势明确、微调收益易证明 |
| 次：工单信息抽取 | 需人工金标 ≥400 条 | 覆盖「信息提取」表述 |

**为什么把主战场从抽取换成行为分类**：抽取微调有天然弱点——prompt + schema 校验往往就能达到不错效果，微调收益不易证明（回滚条款：F1 提升 <3pt 则该任务作废）。而行为分类是天然分类任务，标注成本低一个数量级。

**抽取任务的关键设计：用 schema 强校验替代 prompt 里写「只输出纯JSON」。**

一期现状（继承自 `smart-appointment`）的脆弱性：靠提示词约束 JSON，评测脚本要手写 `priority[:2]` 截断 LLM 自由输出。这个脆弱性本身就是微调任务的动机，也是面试可讲的「问题定义」。

**三向对照实验（简历数字来源）**

| 方案 | 字段 F1 | schema 合规率 | P50 延迟 | 单次成本 |
|---|---|---|---|---|
| B1 prompt-only（一期现状） | 基线 | 基线（低） | 基线 | 基线 |
| B2 + schema 校验 | ↑ | ↑ | 不变 | 不变 |
| B3 LoRA 微调 | ↑↑ | ↑↑ | **显著↓** | **显著↓** |

**数据构造**：输入分布用 agent-desk 真实中文客服语料；金标来自人工修正工单；字段定义沿用 `smart-appointment` 的 `InputParser`。划分 train/dev/test = 6:2:2，**test 集冻结，只在最终报告使用**。

### 3.2 用户行为分析（简历点）

**必须承认的基线事实**：两个参考仓库的「行为分析」本质都是**频次统计**——上游 `preference_manager` 的「学习」是 `confidence_score += 1`（纯计数，无时间衰减、无平滑），`pattern_analyzer` 是频次取 `max()`。仅搬运会被问倒：「这和 SQL 的 GROUP BY 有什么区别？」

**因此三期要补真算法**：

| 能力 | 方法 | 说明 |
|---|---|---|
| 偏好时间衰减 | 指数衰减权重替代 `+=1` | 一行公式，可解释 |
| **意图漂移** | 近30天 vs 前30天意图分布 **JS 散度** | 有明确数学定义，可复现 |
| 流失/升级分类 | 行为特征 → 轻量分类器 | 与 3.1 主任务合流 |
| **自动技能画像** | 从历史工单统计「谁解决过哪些问题」 | **替代一期的人工技能标签** |

**意图漂移是本项目独有优势**：二期 loop 每轮都往 trace 落 `DecisionAction` 与路由意图，**意图序列是免费副产品**。这是「自研 loop + 统一 trace」这个设计决策的自然收益，能讲成完整因果链。

**行为分析的分工原则**：规则算分 + LLM 只组织文案。分数若由 LLM 生成则不可复现、不可回归测试、无法向业务解释。

### 3.3 知识闭环

| 工作项 | 价值 |
|---|---|
| 工单解决方案回写知识库 | 降低后续同类工单量（真实客服系统最易漏、价值最高的一环） |
| 同类问题聚类 → 知识运营工单 | 把重复问题转化为知识建设任务 |
| 关闭原因 → 解决码统计 | 质量分析基础 |

### 3.4 三期验收标准

- [ ] 抽取任务有 B1/B2/B3 三向对照数据，样本量 ≥400 且 test 集冻结
- [ ] 行为分类有明确基线（规则阈值）与量化提升
- [ ] 意图漂移在合成案例上可验证（构造分布迁移，断言漂移值上升）
- [ ] 自动技能画像与一期人工标签对比，报告一致率
- [ ] 知识回写后，同类工单量的下降有前后对比

## 跨期事项

### 贯穿三期的红线

- **样本量不足就写样本量不足，不伪造数字。** 这是面试里唯一会被真正否定的事。
- **评测与业务物理隔离**：业务代码不得 import 评测包，评测不写业务表。
- **每期结束产出可度量的数字**，否则该期不算完成。

### 风险与回滚触发条件

| 风险 | 触发条件（量化） | 回滚动作 |
|---|---|---|
| 一期派单器边界膨胀 | 派单模块 >600 行仍不收敛 | 砍掉「最近响应时长」排序项，只保留专长匹配 + 负载 |
| 一期评测数据集不足 | 指派金标 <100 条 | 缩减到 Top-1 单一指标，报告注明样本量限制 |
| 二期 loop 改造成本超预期 | 二期过半时 loop 模块 >1200 行未跑通 | 去掉中断恢复，只保留单轮 loop |
| 二期 MCP 拖慢进度 | MCP 接入耗时 >3 天 | 退回进程内工具，MCP 延到三期或不做 |
| 三期微调无收益 | 抽取 F1 提升 <3pt | 只报「schema 校验 + 小模型蒸馏」结论，不写微调 |

### 建议的一期启动顺序

1. 技能标签树 + 员工技能关联（方案 A）
2. 确定性派单器 + `TicketAssignmentLog`
3. 评测框架（指派准确率优先）+ 金标数据集
4. 工单全链路（去重 / 补全 / 确认 / 幂等）
5. 单轮 RAG + 真置信判定
6. 4 个模型侧工具 + 治理层
7. CLI 全套

> 顺序理由：派单器与评测是本期主体且互为依据（先有派单才有金标，先有评测才知派单好坏），故排在最前。工单全链路依赖派单器的输出结构，排在其后。
