# P6-b 预约域：占的是"人和时间"，不是"责任"

复现：`make test`（离线 47 条，`tests/test_appointment.py`）、`make probe-p6`（B 段 `visit` 场景真机一轮）。

## 为什么单独立一个聚合

工单占的是"谁负责"，预约占的是"人和时间"。同一条 P0 可以既派了人又约了上门，
两个生命周期互不蕴含：派了人不代表到访，到访了不代表结单。给工单加一个"上门"类别，
等于让一次上门同时是一条 `progress` —— 那条枚举上就会同时挂"谁在做"和"几点去"，
而它们的合法转移完全不同（`booked→visited` 对 `assigned→accepted`）。

## 负载这条线在这里定案（顺手还了派单 v4 挂着的那条裁决）

名册里的 `current_load` 是**运营基线**（一张快照），预约占用是**运行期事实**，
两者相加才回答"这个人现在还能不能接"。所以派单侧必须读同一个视图 ——
`AppointmentStore.staff()` 是那一份视图的唯一出口，`match_service` 的候选人从它里面取。
否则同一份事实在派单和预约两边各有一个答案：派单说"还有余量"、预约说"约不上"。

- `test_派单读的是同一个带占用的名册视图`：约掉一格之后，`match_service` 递出来的 101 号负载立刻 +1。
- `test_提案与写入对还有没有余量给同一个答案`：`propose()` 不再额外减一次 `busy()`（占用已经叠进 load 了）。
  两道闸各减一遍 = "还有没有余量"在提案与写入上给出不同答案，用户就会在"明明可约"的时刻上看见一次失败。

## 时段与闸：每条都是一个会咬人的次序

- 时长只有 30/60/120 三档。排班是按档排的，接受任意分钟数等于伪造精度。
- 整段必须落在同一个工作日的同一个窗口里（跨天上门没有排班可言）；收工时刻**等于**窗口上沿算允许。
- 背靠背不算冲突（`_crosses` 两个严格不等号）：上一单的收工时刻就是下一单的开工时刻。
- **幂等闸排在冲突闸之前**。同一 (人, 时刻, 时长) 的重复提交返回同一条并写明"没有二次占用"。
  顺序反了就会这样：确认闸之后模型再提交一次 → 撞上自己刚建的那条 → 用户看到一次报错。
- 离职者既不被叠占用，也不能承接上门（`with_overlay` 与 `book()` 各一道）。
- 改期在**同一把闸**里重算，不做"先取消再重订"：那两步之间留下一个既不占人也不算取消的空洞，
  而第二步失败时回滚无路。闸拦下时原预约一个字段都不动（`test_改期失败时原预约一个字段都不动`）。
- 占用只按"条数"算：`_assert_placeable` 里 `max_concurrent - current_load - busy`，
  `busy` 是这个人未履约预约的**条数**，不按时间重叠折算。

## 时刻：本地墙钟，两处接缝都是真机撞的

1. 模型递进来的时间总带方言（ISO 的 `T`、秒、`+08:00`）。`_parse_time` **只剥后缀、不做换算**：
   上门比的是本地时刻，悄悄换算会把人挪八小时。判不出来就报错，不猜一个。
2. 框架注入给模型的"现在几点"默认按 UTC 墙钟，而托管路径每轮重组 agent 时只传
   `context_config` 与 `react_config`（`app/_service/_chat.py:1109-1120`），`AgentData` 里没有
   `injection_config` 这个字段 —— 唯一入口是 `custom_agent_cls`，于是有了 `LocalClockAgent`。
   这条对预约是致命的：模型会按 UTC 理解"下午三点"。

## 变更日志是事实源，不是调试输出

`AppointmentStore._log` 每一笔写两处：内存里的 `BookingEvent.detail`（给人看的措辞），
和写穿到 `ledger` 的结构化字段（给 AutoDream 折的）。`at` 用**变更时刻**而不是"现在"
（`test_预约写穿用的是变更时刻不是现在`），否则一次补记的历史会把偏好表折歪。

## 工具话术

- 扫不到格子时说"没人能上门"并给出路（放宽窗口 / 改远程 / 明确约不出来），不许编一个时刻。
- 槽位引文在用户原话里查不到 → 按未填记账，但不拦这次落约（与建单同一套裁决）。
- 待上门清单为空也提醒一句"别凭记忆答"。
- `close_appointment`（登记到场）**不走确认闸**：它记的是已经发生的事，不是对用户的承诺。
  回访结论落在预约上，`resolved` 是三态（None=还没上门），"还没上门"不能读成"没解决"；
  有关联工单就把回访并进它的进展，工单不存在就照实说没并进。

## 一条只有真机会说的接缝

`ask_user` 的槽位枚举加了预约三槽，问句却打的是 `domain._SLOT_LABELS` 那张表 —— 表里只有工单五条，
于是模型把内部字段名原样念给了用户（真机 2026-09-27 20:15：`- 请补充：visit_time`）。
措辞表补成八条、`appointment.py` 里那份重复表删掉（一张表只留一处），
判据换成工具自己生成的 schema：`test_可追问的每一个槽位都有人话措辞` 逐条比对枚举与措辞，
再加一条宽度断言（8）—— 枚举越宽，qwen3 越倾向一次全问出口，这是同一次实测里看到的：
同一句话关臂问了 4 条、开臂问了 8 条。

## 已知边界（没做的，都写清楚）

- 簿还是进程内的（与 `TicketStore` 同一条边界）：服务重启之后预约不在，落盘的只有日志那一层。
- 一份预约簿跟着一个 session：换会话看不见上一次约了什么。跨会话能读到的只有偏好表（P6-a）。
- 没有日历、没有节假日表、没有时区表：可约窗口就是名册里那张班表。
- 预约与工单不双向对账：`ticket_id` 是单向下链，把工单关掉不会取消它的上门。
- `AppointmentStatus.MISSED` 在枚举里、也在"放行占用"的判据里，但**没有任何路径写它** ——
  爽约要么由运营登记（还没有那条工具），要么就永远占着那一格。
