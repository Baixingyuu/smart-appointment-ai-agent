# 指派金标判定说明（RUBRIC）

这套口径是金标的可复现依据：换个人按这份文档标，应当得到同一批答案。
标注前先读这一页，标注中不要回头看任何系统输出。

## 0. 你能看到什么、不能看到什么

看到：工单标题/描述/类别/优先级、下面的组织事实表、`roster_shuffle.csv`。
看不到：任何系统预测（服务命中、判弱、指派候选都不在表里）。表尾员工顺序是随机生成的，顺序本身不含信息。

`期望指派` 一栏填员工号；认为该转人工时填 `ESCALATE_HUMAN`；认为多人同样合理时用 `|` 分隔（如 `105|108`），并在 `可判性` 写 `多值皆可`。

## 1. 判定次序（按这个顺序走，冲突时上位规则赢）

1. **在职优先**：`active=False` 的人（109）永远不能作为答案。
2. **服务归属是强先验**：工单指向某个服务时，默认派给该服务的 owner。归属表是运营定的业务事实，不是提示——真实派单坐席本来就掌握它。
3. **backup 顶上的三种情况**（此时答案从 owner 换成 backup）：
   - owner 无容量：`当前负载 < 上限` 不成立（见事实表，快照冻结，负载按表算）；
   - owner 与工单所需技能明显不匹配（例如数据库集群故障 vs 前端 owner）；
   - owner 就是被指派对象所在的组而工单明确要求跨组隔离。
4. **级别只在"事故 + 高优先级"上加权**：`category=incident` 且 `priority` 为 P0/P1 时，倾向 senior；
   但**不因为"必须 senior"就否掉唯一合格的 mid**——某类问题全公司只有一个人会做时，答案就是他。
5. **实习坐席（108）**：只做前端类工单的 backup 与低风险咨询类；独立复杂故障不能给他。
6. **无归属 / 跨多服务且无法定主责 / 正文信息不足以判断**：填 `ESCALATE_HUMAN`，并在 `可判性` 写 `不可判`（此时 `期望指派` 也填 `ESCALATE_HUMAN`）。
7. **负载都紧**：优先低负载者；同级同负载时选更贴近该服务的人，而不是"最近响应快的人"。

## 2. 什么情况必须转人工（这是最容易标错的一栏）

- 工单同时命中两个互不相容的归口，正文里没有主责线索；
- 需要的能力在名册里根本没有（例如法务/合规之外的采购类诉求）；
- 描述本身自相矛盾或关键信息缺失到"派谁都只能是猜"；
- owner 与 backup 同时无容量，且没有第三候选。

**不要**用"我觉得这题模型会答错"来标 ESCALATE。转人工是运营决定，不是难度决定。

转人工 ≠ 不可判：如果"该转人工"本身就是明确唯一的答案（例如 owner 与 backup 同时无容量、无第三候选），
`可判性` 填 `单值`；只有工单正文自身信息不足以下判断时才填 `不可判`。

## 3. `涉及服务` 一栏（选填，用于错误归因）

## 5. 这份金标能证明什么、不能证明什么（诚实边界）

- 单人标注只能算 **self-agreement**（隔一轮复标 10 条，看自己是否一致），**不是**跨人 κ。
  报告里必须写"单人金标"，不得对外声称这是多人一致的金标准。
- 45 条 ⟹ 每条粒度 2.2pt，低于本仓库自订门槛「金标集 <100 条不得当结论」。
  指派准确率只作方向性证据，「补到 100+ 条」是后续项，不是本轮结论。
- 优先级：`dp-v2-003 / 017 / 023 / 045` 这 4 条在 Go 侧已因重标定确认过期，先标它们。
  「过期」指的是这 4 条在旧标定下锁的层 1 `serviceTop1`；重标它们同时给服务抽取重新定基线。
