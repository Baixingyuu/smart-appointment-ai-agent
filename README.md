# helpdesk-agent

以「评测驱动」的客服工单系统。技术栈 Go，重心在**可复现的评测**而非模型本身。

**一期已完成**：三段派单流水线（服务归属解析 → 加权打分 → 判弱升级 LLM → 人工兜底）、
工单全链路、RAG 真置信判定、模型侧工具与治理层、评测框架、会话与消息模型、HTTP 接口层。

真正的多步 agent loop、查询改写、微调、用户行为分析按计划留待二期、三期。

## 工具与治理

只给模型**三个**工具，边界是刻意的：

| 工具 | 风险 | 说明 |
|---|---|---|
| `rag_search` | 读 | 检索知识库，返回证据与充分性判定 |
| `ticket_find_open_by_topic` | 读 | 查重，避免重复建单 |
| `ticket_create_confirm` | **写** | 发起确认，用户同意后才真正建单 |

**不做成工具的能力**：信息收集（靠对话追问）、派单与优先级计算（确定性业务规则，
留在后端——否则「指派准确率」无法归因）。

**曾有的 `ticket_create_draft` 已移除**：它的 5 个参数中有 4 个与
`ticket_create_confirm` 完全相同，属于设计冗余；它唯一的价值是提前校验字段，
而确认提示里本就会列出缺失信息。移除后工具 schema 从 731 → 434 token，
建单链路也从 5 步降到 4 步。

**参数校验先于确认中断**：早期实现在写操作分支里才解析参数，空标题会先向用户
发起确认、用户同意后才失败——用户白确认一次，还可能建出脏数据。现在如此类非法参数
会被直接拒绝并回灌给模型改正。

## 成本优化实测

固定开销（系统提示词 + 工具 schema）是每一轮都要付的成本，用测试锁进预算：

| 项 | 优化前 | 优化后 |
|---|---|---|
| 系统提示词 | 380 | 332 token |
| 工具 schema | 731（4 个工具） | **434（3 个工具）** |
| **固定开销合计** | 1,111 | **766 token（−31%）** |

**多轮历史是这笔固定开销之外新增的成本**，因此分开计量：模型只看当前消息时
「刚才那个还是不行」这类指代无从解析，所以按窗口注入历史
（默认最近 6 条、单条 220 rune、合计 900 rune，超预算从最旧一条开始丢）。
上面 `overhead_test.go` 锁的 900 只覆盖系统提示词 + 工具 schema，
历史走的是 `messages`，两者不会互相掩盖。

真实模型端到端效果（deepseek-flash，4 场景）：

| 场景 | prompt token | 变化 |
|---|---|---|
| 知识库能答 | 3,326 → **2,657** | −20% |
| 账号锁定 | 3,470 → **2,557** | −26% |
| 建单全链路 | 10,512 → **7,537** | −28% |
| 寒暄（短路） | 283 → 283 | 持平（已是最小） |
| **合计** | 17,591 → **13,034** | **−26%** |

治理层四道闸，每次拒绝都有**结构化归因**（`unknown_tool` / `not_allowed` /
`budget_exceeded` / `args_too_large` / `invalid_args`），使「越权尝试率」
「预算超限率」这类指标可被统计：

```
白名单 → 风险分级 → 预算（总次数 / 单工具次数 / 参数体大小）→ 确认拦截
```

所有工具参数都给**真实 JSON Schema**。参考实现把兼容别名的参数统一写成
`{"additionalProperties": true}`，模型看不到参数含义只能靠猜，工具调用准确率因此无法提升。

## 确认中断-恢复

写操作**不阻塞等待**，而是落一条中断，由用户的下一条消息触发恢复：

```
用户：帮我建个工单
  → 模型调 ticket_create_confirm（写操作）
  → 落 pending 中断，回复确认文案（工单尚未创建）
用户：确认
  → 恢复：执行建单 + 按服务归属自动派单 → resolved
用户：算了，先不用
  → 恢复：标记 cancelled，不建单
用户：还是没弄好，再帮我建个单跟进
  → 判定为新一轮建单诉求：不拿上一轮定下的旧草案建单，
    带上下文交给模型重新处理
用户：这个我再确认一下影响范围再说
  → 语义不明：带上下文（历史 + 「一份工单正等待确认」的说明）再问一次模型，
    草案保持 pending
```

待确认期间来的消息**必须被处理，不能被确认状态机吞掉**。
判定阶梯是 `新诉求 → 取消 → 确认 → 语义不明`，纯词表、可单测；
表达（怎么问、怎么重述）交给模型。语义不明不猜测，但也**不沉默**——
早期实现是「原样重发确认文案、不调模型」，代价是这条用户消息被直接丢弃
（实测该回合 `promptTokens=0 / rounds=0`），已修复为带上下文再问模型。
新诉求与语义不明共用同一条回落路径，分成两个枚举值只为让词表判定可单测、可归因。

`确认` 在中文口语里经常不表示批准，因此有一张确认否决短语表：
自述核实（「确认一下」「核实一下」）、否定式（「不确定」「无法确认」）、
延后表态（「再说」「稍等」）命中任一即不算批准——纯子串匹配会把
「这个我还不确定」判成批准并真的建单。

选择中断-恢复而非同步阻塞：真实客服场景中用户可能几小时才回复，
同步阻塞会因超时丢单并占用连接。因此**恢复所需的全部数据都落库**，
进程重启后仍能恢复。

安全约束：
- 只有 `DecisionConfirm` 能触达建单；这条不变式由 `TestOnlyConfirmGrantsApproval`
  与编排层的「建单必须体现在工单列表里」断言共同守住，不靠回复文本
- 只有 `pending` 状态可恢复，已 `resolved`/`cancelled` 的中断不可再恢复（防重复建单）
- 同一会话起新草案时，旧草案标记 `superseded`：查找待确认中断取「最新的 pending」，
  旧草案若仍 pending，最新草案一旦被解决就会回落到用户从未见过的陈旧草案（幽灵确认）
- 超过 `ConfirmTTL`（默认 2 小时）判定过期，不执行，草案标记 `expired` 后交回模型
- 语义不明时**不猜测**，保持 pending 让用户仍可确认
- 两个终态口径必须分开：`Interrupted` 指「本轮新起了一个确认」，
  `AwaitingConfirmation` 指「会话当前仍有待确认草案」；评测断言用后者

## HTTP 接口

```
GET  /api/health                              健康检查（含当前模型模式）
POST /api/conversations                       创建会话
GET  /api/conversations                       会话列表
GET  /api/conversations/{id}                  会话详情（含全部消息）
POST /api/conversations/{id}/messages         发送消息（幂等）
POST /api/conversations/{id}/close            结束会话
GET  /api/tickets            GET /api/tickets/{id}     工单列表与详情
GET  /api/employees                                   处理人（含实时负载）
```

```bash
# 一次完整交互
CONV=$(curl -s -X POST localhost:8080/api/conversations \
  -H 'Content-Type: application/json' -d '{"title":"接口问题"}' | jq -r .id)

curl -s -X POST localhost:8080/api/conversations/$CONV/messages \
  -H 'Content-Type: application/json' \
  -d '{"content":"接口返回 401 怎么办","requestId":"req-1"}'

# 用同一 requestId 重试 → 返回 {"duplicate":true}，不会重复落消息或重复建单
```

**幂等设计**：`requestId` 是幂等键。客户端未提供时服务端按「会话 + 内容」派生，
至少能拦住「同一句话被重复提交」这种最常见的重复。响应里用 `duplicate` 标记
而非报错，便于调用方区分「重复」与「真失败」。

**会话关闭后**发消息返回 `409`（状态冲突，客户端可纠正），而不是 `500`。

**错误格式统一为 JSON**：标准库对未匹配路径/方法会写纯文本，服务对其做了改写，
避免客户端按统一格式解析时失败。

需要 Go 1.24+（`brew install go`）与 python3（仅用于评测集校验）。

国内网络下 `proxy.golang.org` 可能不可达，需配置：
`go env -w GOPROXY=https://goproxy.cn,direct`

## 检索：默认 BM25

离线默认用 **BM25**（`internal/rag/bm25.go`）而非向量检索，理由：

- 企业客服知识库以词面重叠为主（用户问「接口 401」，文档写「接口返回 401」），
  BM25 在这类场景表现接近甚至优于小模型的稠密向量
- 不需要任何外部服务与 API Key，离线评测完全可复现
- 打分可解释：分数来自具体词项权重，便于归因

三个来自实测的设计细节：

1. **中文用字符 bigram，英文数字用整词** —— 中文无词边界，引分词词典会带来依赖；
   而英文若也切 bigram 会把 `401` 切成 `40`、`01`，引入噪声。
2. **分数归一化到 0..1** —— 原始 BM25 分数随语料规模变化，除以「该查询的理论满分」
   后与余弦相似度同量纲，门控阈值才能通用。
3. **词表外词项不进入覆盖率分母** —— 口语填充词（「老是」「是什么」）从未出现在
   知识库中，计入分母会稀释覆盖率，实测导致正确文档被判为「证据不足」，
   模型因此反复改写查询重试。

生产环境要语义检索时，把 `seed.NewBM25Retriever` 换成 `rag.NewOpenAIEmbedder`
即可，检索、门控、工具层都不受影响。

## 真实模型实测（DeepSeek flash）

```bash
DEEPSEEK_API_KEY=sk-xxx go test ./internal/agent/ -run TestLive -v
```

未设置密钥时该测试自动跳过，因此 CI 与离线检查不受影响。
它的价值是暴露**离线桩模型发现不了的问题**——实测已据此发现三个真实缺陷：

1. **预算对真实模型过紧**：真实模型单轮并行发起 2-3 个工具调用，
   而 `MaxTotalCalls: 4` 是按「一次调用一个工具」设的，
   导致正常的「检索→查重→起草→确认」链路在第三步被打断。
2. **思维链模型必须回传 `reasoning_content`**：DeepSeek flash 运行在 thinking 模式，
   下一轮请求缺失该字段直接返回 400。丢弃它会让 Agent 在这些模型上完全无法运行。
3. **检索质量决定成本**：用字符哈希投影时模型不信任检索结果、反复改写查询重试，
   单轮 prompt 达 9,600 token；换 BM25 后降至 3,100 token（**−68%**），
   耗时从 6.6s 降至 2.3s。

当前实测基线（4 个场景，deepseek-flash + BM25）：

| 场景 | 轮次 | prompt token | completion token | 耗时 |
|---|---|---|---|---|
| 知识库能答 | 1 | 3,113 | 290 | 2.3s |
| 账号锁定 | 1 | 3,009 | 356 | 2.8s |
| 知识库未覆盖（含建单确认） | 1 | 12,138 | 1,036 | 7.1s |
| 寒暄 | 1 | 1,395 | 159 | 1.5s |
| **合计** | | **19,655** | **1,841** | |

> 单轮 prompt 约 1,400 token 是固定成本（系统提示词 + 工具 schema）。
> 建单场景偏高是因为要走完 5 轮决策，每轮累积证据与工具结果。

## 派单算法：三段流水线

派单的第一因是**谁负责这个业务**（服务归属），不是标签相似度——技能层曾作为匹配维度，
已于 2026-09-24 整体删除，理由见 `docs/DISPATCH_PIPELINE.md §1.4`。

```
Stage 1（确定性，近零成本）
  1.1 resolve    BM25：工单文本 → 服务节点（top-3 + 命中下限 0.25）
  1.2 kNN        相似历史工单的处理人（接口先立，当前无历史语料 → 空返回）
  1.3 filter     不在职 / 满载（实时未完成数）/ P0 未达 senior 门槛
  1.4 score      own 0.40 + sim 0.20 + avail 0.20 + seniority 0.10 + recent 0.10
                 ownership 档位：owner 1.0 / backup 0.3 / team 0.1
  1.5 weakness   离散判弱：low_margin(<0.15) / no_service_match / empty_candidates
        ↓ 强判定 → 直派；判弱 → Stage 2
Stage 2  LLM function-calling，assignee_id 被 enum 锁死在 Stage 1 的 top-5 + ESCALATE_HUMAN
Stage 3  人工待认领池（无候选 / 模型主动升级 / 模型给出候选集外 ID 三种入口都汇到这里）
```

排序决胜是确定性的：总分 → 负载 → 响应 → 员工 ID 升序，总分比较用 epsilon 容差。
每条 `AssignmentLog.Reason` 带 `[path=...|weakness=...]` 前缀，"走的哪一段、为什么升级"能直接 grep。

## LLM 在派单里只做一件窄决策

派单**不是**纯规则、也**不是**纯模型：强命中由 Stage 1 直出，只有判弱样本才交给模型，
且模型只能在候选集内选。这样切分是为了同时守住三件事：

- **可复现**：Stage 1 同输入同输出，回归测试才有意义；
- **可解释**：每个结果带分项评分明细与可读理由；
- **可归因**：Stage 2 的幻觉 ID 不重试，直接转人工并计入 `PathStage2Invalid`——
  把"幻觉率"当独立指标，而不是藏在派单准确率里。

成本账也必须摊开：Stage 2 一次调用约几分钱、1-3 秒，且会给轨迹评测的轮次/延迟/token
三个轴引入噪声，所以离线评测刻意不注入 chooser。接入真实模型跑 Stage 2 的开关是
`eval-assign-v2 -offline-stage2=false`。

## 工单状态机

```
pending --accept--> in_progress --resolve--> done
   |                     |
   +------ escalate ------+   （排除当前处理人后重新派单）
```

- **`in_progress` 必须显式接单进入**：参考实现中该状态从不由代码路径自动设置，
  导致「处理中」实际不可达；且跳过接单直接完成会被拒绝。
- **建单不阻塞于信息不全**：缺失字段记入 `MissingInfo` 并写入进展，
  而不是拒绝建单——真实场景中用户常无法一次说清，卡住会让问题丢失。
- **同一会话已有未关闭工单时去重**：追加一条进展而非新建，
  避免用户反复追问产生大量重复工单。
- **升级会排除原处理人**：否则重新派单大概率又落回他身上——他正是这个服务的归属人。
  被排除者仍留在候选明细里并标记原因，使「为何换人」有据可查。

## 意图路由与成本

系统在进入工具链路前先做意图分类，用于两件事：**让路由准确性可度量**，
以及**让不需要工具的输入短路**（原设计中路由是隐式的，靠模型选工具，无法单独度量）。

```
用户消息
  → 意图分类（一次极短调用）
      ├ chitchat / out_of_scope / handoff → 短路：一次短回复，不进工具循环
      └ knowledge / incident              → 完整链路：检索 → 工具 → 建单
```

顺序上有两个必须守住的约束：**确认恢复优先于分类**（用户回复「确认」按语义属于
chitchat，先分类会被短路掉建单确认）；**分类失败回退到完整链路**
（行为与无路由版本一致，只是丧失短路的成本收益）。

**分类准确率**（180 条中文样本，5 类，deepseek-flash）：

| 方案 | Accuracy | Macro-F1 |
|---|---|---|
| 离线关键词规则（零成本基线） | 54.44% | 0.5243 |
| **真实模型** | **98.33%** | **0.9813** |

**成本影响**（实测，4 场景）：

| 场景 | 短路 | prompt token | 对比无路由 |
|---|---|---|---|
| 寒暄 | ✅ | **283** | 1,395 → 283（**−80%**） |
| 知识库能答 | 否 | 3,313 | +200（分类开销） |
| 账号锁定 | 否 | 3,225 | +216 |
| 建单全链路 | 否 | 11,088 | −1,050 |

寒暄类的一次交互成本降了 80%；访问知识库的场景多付约 200 token 的分类开销
（换来可度量的路由准确率与更好的意图消歧）。整体是否净收益取决于流量分布——
高频寒暄的客服入口收益明显，纯知识库问答场景需按比例核算。

| **执行轨迹** | `trajectory.json` | 工具选择准确率、顺序准确率、平均轮次、**安全越界率**、预算超限率 |
| 成本与延迟 | 同上 | prompt token 合计、端到端延迟 P50/P95/Max |

**检索轴的假命中率是最容易被忽略、后果却最严重的指标**：召回率只看「该找到的找到了多少」，
而假命中意味着模型基于无关片段作答。实测优化过程：

| 版本 | Recall@5 | 假命中率 | 可回答且有证据 |
|---|---|---|---|
| 初版门控 | 92.50% | **70.00%** | 58/80 (73%) |
| 加命中词项数判据 | 92.50% | **10.00%** | 44/80 (55%) |
| 改用原始分数判据 | 92.50% | **10.00%** | **69/80 (86%)** |

中间那一步是典型的两难：压住假命中的同时把召回也压掉了。
根因是**归一化分数无法区分两类查询**（可回答中位数 0.44、不可回答 0.46，几乎相同），
换用原始 BM25 分数后两者才分开。详见 `docs/EVALUATION.md` 第 3.5 节。

**指标刻意分轴统计。** 若把工具选择与其他断言混成一个数字，就无法判断一次退化
究竟是「模型选错了工具」还是「步骤多了一步」——而这两者的改进方向完全不同。

### 评测区分力的自证

指标好看不等于评测评得出问题。因此提供 `-sabotage` 注入已知缺陷，
并要求指标相应下降（实测数据）：

| 注入缺陷 | 通过率 | 工具选择 | 顺序 | 安全越界 | 平均轮次 | 被命中的指标 |
|---|---|---|---|---|---|---|
| 无（基线） | 100.0% | 100.0% | 100.0% | 0.0% | 1.67 | — |
| `skip_rag` 跳过检索 | 33.3% | **0.0%** | 0.0% | 0.0% | 1.67 | 工具选择 |
| `always_write` 总是建单 | 33.3% | 58.3% | 0.0% | **47.6%** | 1.14 | 安全越界 |
| `extra_rounds` 多余步骤 | 14.3% | 25.0% | 0.0% | 9.5% | **5.67** | 平均轮次 + 预算超限率 100% |
| `unknown_tool` 编造工具 | 14.3% | **0.0%** | 0.0% | 0.0% | 2.67 | 工具选择 |

> 按 21 条样本（2026-09-23，新增 tj-021「待确认期间语义不明」用例）重测。
> 四种注入下**原有用例的通过集合与 20 条时逐条一致**（7 / 6 / 3 / 3 条），
> 没有任何一条因修复而从失败变通过或反向；比率的漂移只来自分母变 21
> 以及新用例自身——它在 `skip_rag` / `extra_rounds` / `unknown_tool` 下失败，
> 在 `always_write` 下通过：该脚本只把首轮演到「发起确认」，第二轮的语义不明
> 走状态机回落、拿到的是队列末尾那条纯文本回复，因此不触达建单。
> 也就是说交互契约修复没有让评测变钝。

上面四种注入打的是**模型脚本**。词表侧还有一次代码侧变异实验：
临时摘掉 `ParseConfirmationDecision` 的确认否决守卫后重跑脚本评测，
21 条里**只有 tj-021 失败**（「工单创建状态不符：期望 false，实际 true」
与「终态中断状态不符：期望 true，实际 false」同时命中），
说明这条用例真的按在缺陷上，而不是靠模型配合才通过。

**⚠️ 关于「基线 100%」的解读**：脚本模式（默认，无密钥）下的脚本化模型是
「照着期望演」的，因此 100% 是**评测链路与断言的一致性检查**，不是模型能力评估。
提供 `-api-key`（或 `LLM_API_KEY`）后，同一套评测与断言切换为真实模型驱动
（并注入与 serve 一致的意图分类器），报告标注 `mode: live`，产出真实能力测量：

```bash
LLM_API_KEY=sk-xxx make eval-trajectory ARGS="-json eval/reports/trajectory_live.json"
```

## 评测设计：派单轴

一条轴、一份数据集、三轴指标：

| 数据集 | 条数 | 构成 | 指标 |
|---|---|---|---|
| `assignment_v2.json` | 45 | 26 条手写 + 19 条由 [Console-AI/IT-helpdesk-synthetic-tickets](https://huggingface.co/datasets/Console-AI/IT-helpdesk-synthetic-tickets)（MIT）改写场景 | 抽取 / 判弱 / 排序三轴 + Stage 漏斗 |

样本形态与真实工单同粒度（口语标题 + 一段描述），每条带期望服务、期望判弱原因、
期望 outcome 与期望处理人。金标分布：`matched` 40 条 / `fallback_pool` 5 条，
判弱原因 `none` 40 / `no_service_match` 3 / `low_margin` 2。

实测（2026-09-24，离线）：

| 轴 | 结果 | 有效分母 |
|---|---|---|
| 抽取 service top-1 | 42/45 = 93.33% | 45 |
| 判弱原因一致 | 38/45 = 84.44% | 45 |
| 排序 winner 一致 | 34/40 = 85.00% | **40**（兜底池样本没有期望处理人） |
| Stage 漏斗 | stage1=35 / stage2=0 / stage3=10 | 45 |

**没有一轴是 100%，这是有意的。** 逐条复核后，8 条不一致分成两类，各 4 条：

- **金标过期**（`exp=none got=low_margin`）：`ownershipScore` 重标定
  （owner/backup/team 由 1.0/0.6/0.3 改为 1.0/0.3/0.1）只改了实现，金标仍停在标定前。
- **服务解析召回**（4 条）：dp-v2-036 期望无匹配却召回 2010、dp-v2-038 期望 2007 得 2003、
  dp-v2-041 期望 2005 得 2014、dp-v2-007 该命中的服务没达下限。
  其中 dp-v2-038 / dp-v2-041 连带排序判错——派错服务就派错人。

**刻意没有重打金标把分数抬上去**——那等于用实现去定义正确答案，闸门立刻变成自证。

### 金标防线换了一道，代价要写清

v1 曾有 `gen_hard_dataset.py`（生成）与 `verify_datasets.py`（校验）两套独立实现，
校验侧用 `fractions.Fraction` 精确有理数复算、不 import 生成器，为的是避免
"校验只能证明代码等于自己"。这两份脚本连同 150 条技能数据集已随技能层删除，
**当前派单轴不再有第二套独立实现做交叉校验**。替代的防线是
`internal/eval/pipeline_v2_test.go` 的三条：

1. **金标 ↔ 数据一致性**：每条期望服务 ID 必须存在于服务字典、期望处理人必须存在于
   员工扩展表；`matched` 必然对应 `weakness=none`，`fallback_pool` 必然 `assignee=0` 且带归因。
   这防的是"金标与目录脱钩"（改了种子忘了改金标）。
2. **区分力**：断言赢家至少覆盖 3 个不同员工。若所有用例都派给同一个人，
   通过率再高也是废指标。
3. **回归下限**：把 §实测 的四个数字锁成下限，退化即红；改进要显式改基线。

## ⚠️ 关于这几个数字的边界

数据集的 `goldSource` 字段写的是 `formula-derived`：**金标由派单规则推导**。
因此三轴数字证明的是「实现 == 我们宣称的规则」，不是「派单派得准」。
真实准确率需要 **"工单 → 人工实际指派"的历史数据**，排在三期；
在此之前不要把这些数字写进任何对外材料。

同理，Stage 2 的命中率与幻觉率目前是**未测**，不是 0%：离线评测刻意不注入 chooser。
接线已经留好（`make eval ARGS="-offline-stage2=false -api-key=..."`），
只有接上真实模型跑出来的那一格才算数。

internal/llm/           模型客户端（官方 OpenAI SDK）+ 可注入接口

internal/agent/         回合编排：工具调度、确认中断与恢复、token 累加

### 四条设计红线

1. **评测是观察者**：业务代码不得 import `internal/eval`，评测不写业务表。
2. **Stage 1 是纯函数**：无 I/O、无时间依赖、无随机，因此可直接单测、可锁回归下限。
   整条流水线唯一的外部调用是 Stage 2 的 LLM chooser，它被两道约束包住：
   候选 ID 由 enum 锁死，出错（含幻觉 ID）一律转人工而不是重试。
   离线评测干脆不注入 chooser，所以确定性那一半永远可复现。
3. **依赖方向单向**：`domain` ← 其余所有包。建单输入类型定义在 `domain`，
   使 `seed` 等工具包无需反向依赖业务层。
4. **授权与流程分离**：`tooling.Authorize` 只判断「能不能调用」，
   不判断「流程走到哪一步」。写操作的确认由编排层负责落中断——
   两者混在一起会让确认流程失去落点（实测踩过）。

## 已发现的坑（记录备查）

1. **等权权重是错的，且一次定终身也是错的**：负载分差可达 1.0，业务相关度分差同样封顶 1.0，
   等权下「最闲的人」会盖过「负责这个服务的人」。改成 own 0.40 主导后，v2 评测又暴露了
   反向问题：backup 档位给 0.6 时，强命中被 seniority/recency 的噪声吃进 `low_margin` 带，
   Stage 1 直出只剩 24/45；压到 0.3 才升到 35/45。权重得由评测轴驱动。
2. **只检验过滤的样本会在排序轴上白拿分**：v2 的 45 条里 5 条 gold 是兜底池，
   它们没有期望处理人，所以**排序轴的有效分母是 40**。按 45 折算会凭空掉 11 个点，
   反过来把 40 报成 45 就是虚报。每条用例适用哪些轴必须写进断言，不能靠人记。
3. **`fallback_pool` 保留候选明细但不正式指派**：退回待认领池时 `AssigneeID=0`，
   `Candidates` 仍带完整分项与 `FilterReason`，人工因此能看到「系统建议谁、为什么没派」。
4. **理由是给人看的，必须与实际决胜因素一致**：早期用浮点直接比较分项，
   而 1/3 之类权重在二进制下无法精确表示，导致「归属分实际相同」被写成
   「归属分更优」。已改为 epsilon 比较，并补充了覆盖三种决胜因素的归因测试。
5. **权重 0.00 的特征比没有这个特征更糟**：技能层最后的形态是 `s_skill` 权重归零、
   `Employee.Skills` 与 120+30 条技能数据集原样保留，理由写的是"降级为排序段回归"。
   实际效果是让人误以为技能匹配还在被评测，而没有任何端到端指标依赖它。
   2026-09-24 整体删除：实体、打分特征、数据集、派单器一起走。
6. **负载必须用实时数据**：不采信 `Employee.CurrentLoad` 静态快照，
   而以工单表中未完成工单数重算，否则负载会随时间失真。
7. **确认拦截不能放在授权阶段**：早期实现让 `Authorize` 对未确认的写操作
   直接返回错误，导致调用方在创建确认中断**之前**就短路，
   所有建单用例都拿不到中断。确认是工作流分支，不是授权失败。
8. **单字关键词不能做确认词**：确认词表里的「是」会被「这是」「但是」「不是」
   大量命中，实测「这是什么意思」被判成确认——在写操作场景下这是危险的误判。
   英文还必须整词匹配，否则 `"yes"` 会命中 `"yesterday"`。
